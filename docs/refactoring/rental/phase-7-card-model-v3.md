# Фаза 7 — новая модель карточки и раскладка справочников

Цель: карточка описывает квартиру, а не склейку четырёх форм. На площадку — два рабочих файла.

**Контрольная точка владельца.** Фаза делится на 7a (предложение) и 7b (реализация).
7b начинается только после того, как владелец утвердил предложение 7a.

## 7a. Предложение модели (только документ, код не менять)

Создать `docs/refactoring/rental/card-model-v3.md`:

1. Список понятий карточки (ориентир — 20–40), сгруппированных по смыслу. Для каждого:
   id, подпись, тип, единица, варианты (стабильные латинские коды + подписи), обязательно ли
   хоть на одной площадке. Типы из небольшого набора:
   `text`, `longText`, `integer`, `decimal(unit)`, `money{amount,currency}`,
   `triState` (да / нет / не указано), `enum`, `multiEnum`, `address`, `photos`,
   `list<…>` для повторяющихся групп.
2. Таблица «старое поле → новое понятие» для всех ~120 полей текущего common, с пометкой
   `перенос`, `объединение`, `уходит в mapping как константа`, `удаляется (почему)`.
3. Решения по известным проблемам из ревью (раздел «Модель данных»):
   - числа как числа (площадь, этаж/этажность, цена);
   - один тип «да/нет/не указано» вместо пяти способов;
   - коды вариантов латиницей, подписи отдельно и внутри поля;
   - метро — `list<{station, minutes, mode}>`, телефоны — `list<{number, messengers}>`;
   - минские справочники (метро, микрорайоны) — зависимые от города;
   - одно понятие «Фотографии».
4. Для каждой площадки — какие поля формы закрываются новыми понятиями и что становится
   `manual` или константой.
5. Открытые вопросы владельцу — коротким списком.

Записать в `progress.md` «Фаза 7a — ждёт утверждения» и остановиться.

## 7b. Реализация (после утверждения)

- Раскладка:
  `data/rental/apartments_long_term_rent/card.json`,
  `platforms/<id>/mapping.json` (нативные поля формы с типами, кодами, условиями + правило
  получения из карточки), `platforms/<id>/form.json` (бывший `runtime/browser_<id>.json`).
  Исходные схемы и всё исследовательское — в `research/`.
- Скрипт-конвертер старых файлов в новые (одноразовый, в `scripts/`, после фазы удалить
  или оставить в `research/tools/`). Полученные файлы вычитать и поправить вручную там,
  где конвертер не может решить однозначно.
- Миграция сохранённых карточек в v3 — командой, как в фазе 2.
- Удалить `common.json`, `runtime/card.json`, `runtime/preparation_*.json`,
  `manifest.json` старого формата, `CardProjection`, `addressProjection`.
- Фронтенд: редактор строится по `card.json` (через ответ сервера), включая `list<…>`
  для метро и телефонов.
- Отчёт покрытия (фаза 4) до и после — в PR: новое покрытие не хуже старого ни на одной
  площадке.
