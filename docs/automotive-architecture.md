# Автомобили → Легковые

Категория `cars_used_sale` предназначена для продажи легковых автомобилей с пробегом. Раздел находится рядом с «Недвижимостью»; последняя выбранная секция хранится отдельно для профиля. Карточки сохраняются в памяти при переключении разделов, после перезагрузки значения не восстанавливаются. Серверных черновиков нет.

## Справочник и идентичность

Исходные схемы и browser bindings: `data/parsing/cars_used_sale/`. Команда `node scripts/build-cars-catalog.mjs` создаёт общий справочник, четыре прямых маппинга и индекс `data/automotive/cars_used_sale/runtime.json`. Индекс включается в backend JAR. Не редактировать сгенерированный индекс вручную.

Деревья: марка → модель → поколение и область → город. Остальные перечисления плоские. Год — отдельное числовое поле; поколения не отфильтровываются по нему. Модификации не используются.

У каждого общего варианта постоянный `car.option.<uuid>`. Файлы `identity-registry.json` и `source-identities.json` нужно хранить вместе с каталогом: они защищают ID при повторной сборке и переименовании источника. Удаление этих файлов изменит идентичность вариантов. Нативный `value` площадки, её ID справочника и общий ID — разные сущности.

Объединение названий выполняется внутри соответствующего родителя. Правила находятся в `scripts/cars-canonicalization.mjs`: регистр, пробелы, ё/е, Series/серия, Klasse/Класс, явные синонимы, обозначения рестайлинга, коды кузовов и номера поколений. По согласованной политике спорные обозначения внутри марки и модели объединяются в пользу совпадения: одинаковый номер поколения и рестайлинг, пересекающиеся наборы кодов, семейства G2x/G20/G21. Разные явно указанные рынки, номера рестайлинга и противоречащие номера поколений остаются раздельными. Не удалять дефисы безусловно: Saab 93 и 9-3 — разные модели.

Это не утверждение, что все объединённые площадочные варианты взаимозаменяемы по кузову или рынку. Если площадка разбивает общее поколение на несколько вариантов, выбирается воспроизводимый основной вариант, а все исходные ID сохраняются в `evidence/common-review.json` вместе с `selected` и `resolution: preferred_native_variant`. Предпочтение: больше известных дочерних вариантов, затем лексикографический исходный ID. Полный перечень объединённых имён и исходных ID находится в `evidence/canonicalization-review.json`. Исходные схемы не переписываются.

У совпадающих моделей могут быть разные нативные родители поколений. Поэтому прямой маппинг содержит `paths[commonId]`: полную исходную цепочку выбранного узла. Например, общая BMW «2 серия» на Kufar имеет ветки `model_2er` и `model_2serija`; F22 и G42 должны использовать свою ветку. Бэк сначала использует готовый путь выбранного поколения, затем обычный поузловой маппинг. Расширение получает уже разрешённые значения.

Слияние существующих ID требует явного запуска `node scripts/build-cars-catalog.mjs --review-identities`; обычная сборка новые слияния блокирует. `identity-merges.json` фиксирует перенаправления; `identityAliases` в runtime позволяет принять старый общий ID и вернуть актуальный. Повторная сборка должна давать тот же runtime.

Название модели, повторённое в нативном поле поколения (например, Audi A2 → A2), не является общим поколением. Такие записи исключаются из общего дерева и кандидатов ИИ; исходная схема сохраняется. Старый общий ID такого варианта переводится на модель, а не на выдуманное первое поколение. Если единственный нативный вариант площадки — имя модели, выбранное пользователем настоящее поколение может переноситься в него как в укрупнённый вариант (`match: model_placeholder`). Выбор одной модели не заполняет поколение. Отчёт: `evidence/model-generation-placeholders.json`. Совпадающие с именем модели настоящие римские номера (например, I) не удаляются.

Коды поколений сравниваются внутри модели независимо от скобок и разделителей. `F74-78`, `F74, 78`, `F74/F78` — F74/F78 без выдуманных промежуточных кодов. Уточнение Gran Coupe/GT может объединиться с тем же кодом без уточнения; явно различающиеся типы кузова и рестайлинги остаются раздельными. Если во всей модели известно единственное нумерованное поколение и единственное семейство кодов для той же стадии рестайлинга, они сопоставляются по принятой политике предпочтения совпадений (например, Audi A2: I и 8Z).

Карточка хранит один выбранный узел на корень. Например, `values["car.brand"] = <общий ID Rio>` определяет Kia → Rio; неизвестное поколение остаётся пустым. При выборе поколения предки восстанавливаются по `parentId`. `finalId` отсутствует. Неподдерживаемый узел не заменяется первым вариантом площадки.

## Разделение ответственности

Проверка исходных 1961 поколений с покрытием 3/4 воспроизводится командой `node scripts/review-cars-generations.mjs`. Исходный состав сохранён в `evidence/three-platform-review-baseline.json`; актуальные кандидаты, отсутствующие площадки и причина решения для каждой записи — в `evidence/three-platform-review.json`. Проверка относится к сохранённым схемам и не доказывает отсутствие варианта на живом сайте. Подтверждённые совпадения записываются отдельно в `data/automotive/cars_used_sale/reviewed-generation-mappings.json` (`--write-mappings`); сборка повторно проверяет доказательство, родительскую модель и нативный ID. `match: reviewed_generation` сохраняет отдельные общие ID и полный путь площадки.

При сравнении явных кодов допускаются префикс `Typ`, оформление скобок/пробелов, кириллические двойники латинских букв. Код или группа кодов должны совпасть полностью, фаза рестайлинга сохраняется; противоречащий номер поколения не обходится через alias без номера. Только для BMW обозначения семейства `Fxx`, `E8x` допускают направленный перенос конкретных кодов соответствующей длины. Эти правила не разрешают угадывать связь между римским номером и неизвестным заводским кодом. Лексические исправления моделей имеют явные aliases; `Wagon R` и `Wagon R+` остаются разными.

Направленные соответствия поколений создаются `scripts/cars-generation-fallbacks.mjs`: конкретное поколение → более общий нативный вариант в той же модели (`match: broader_generation`, `broader_common_option_id`). Например, BMW `G12 (Long)` → `VI (G11/G12)`. Сохраняются фаза и номер рестайлинга; код должен входить в явную группу кодов назначения либо совпадать номер поколения при отсутствии кодов у назначения. Известное уточнение кузова/рынка можно опустить, но нельзя заменить другим. Нативный `(FB)` не считается просто `IV` для регионального варианта Kia: заводской код сохраняет смысл.

Точные соответствия не заменяются. Неоднозначные назначения пропускаются; цепочки fallback не используются. Общие ID, aliases и исходные ID не объединяются: эти правила работают только при переносе на площадку, а не при обратном распознавании. Полный нативный путь берётся от общего варианта назначения, с сохранением конкретного общего ID в последнем узле. Отчёт всех добавлений: `data/parsing/cars_used_sale/evidence/generation-broader-mappings.json`.

Список поколений и распознавание ИИ допускают только узлы с утверждённым маппингом на все четыре площадки. Фильтр применяется до поиска и пагинации; передача скрытого ID через selection/prepare также отклоняется. Исходные схемы, полное дерево и ID сохраняются для дальнейшего исследования. Уже утверждённые укрупнённые соответствия `model_placeholder` учитываются; их перечень и отсутствующие площадки для каждого поколения находятся в `evidence/generation-availability.json`. Марки, модели и плоские характеристики этим правилом не фильтруются.

При распознавании поколения сначала проверяются полное название и aliases внутри выбранной модели. Если единственного доступного совпадения нет, текст в скобках во входном названии удаляется и поиск повторяется: `IV (FB)` → `IV`. Единственное точное совпадение имеет приоритет. Неоднозначность после упрощения оставляет поколение пустым и требует уточнения; первое поколение автоматически не выбирается.

* Angular: отображает метаданные, запрашивает варианты с пагинацией и выбранным родителем, хранит состояние формы, приводит ввод чисел к JSON-числам. Зависимые ответы устаревшего запроса игнорируются. Маппингов площадок во frontend нет.
* Controllers: проверяют сессию и передают запросы application services. API: `/api/workspace/categories/cars_used_sale/{editor,options,selection,analyze,recognize-photos,prepare,extension-config}`. Для справочников GET, для операций POST.
* `CarCatalogService`: варианты, пути и проверка принадлежности ID полю. `CarPreparationService`: прямой маппинг, условия доступности, единицы, зависимости и рецепты. `CarReference` — порт загрузки данных; JSON-реализация находится в infrastructure.
* AI: один запрос распознаёт коллаж, другой анализирует оба текста. Полное дерево не передаётся. Названия марки, модели, поколения и географии сопоставляются сервером локально с именами и aliases внутри выбранного родителя. Плоские варианты передаются короткими кодами запроса; сервер преобразует их в общие ID и проверяет принадлежность полю. Пользовательские значения не перезаписываются.
* Расширение: применяет уже подготовленные значения и проверяет результат в DOM. Оно не распознаёт автомобиль и не определяет соответствия между площадками. Использует существующие задания, хранилище фотографий и разрешение на заполнение конкретного документа. Reload/history не разрешают новый перенос.

Цена передаётся без конвертации валют. Валюта устанавливается перед ценой. Пробег — километры, единица устанавливается перед значением. Литры переводятся в см³ AV.by только точно; Kufar получает точный вариант объёма из своего списка. Для AV.by белорусский телефон разделяется на код страны и девять цифр, неизвестный формат требует ручного ввода.

## Плоские списки

Правила `scripts/cars-flat-options.mjs` объединяют написания «5 / 5 мест», «Кожа / Натуральная кожа», «Комбинированный / Комбинированные материалы», «Светлый / Светлый салон» и варианты пробелов в названиях городов внутри одной области. Отчёт `evidence/flat-options-review.json` перечисляет все проверенные оставшиеся общие списки и дополнительные списки площадок.

Дополнительные поля: `enum` отправляется строковым ID, `multi_enum` — массивом ID, `boolean` — булевым значением (включая `false`). «Не указано» удаляет поле из `extras`, пустой ID не отправляется. В Angular одиночный и множественный `select` создаются отдельными ветвями шаблона: динамический `[multiple]="false"` всё равно подключает множественный value accessor и превращает одиночный выбор в массив. Подписи дополнительных полей связаны с контролами через `for`/`id`.

Состояние «С пробегом» для Kufar/Onliner и единицы общего пробега (километры) для Onliner/AV.by назначает сервер подготовки. Эти параметры не предлагаются как редактируемые дополнительные поля. UI-регрессия `scripts/test-car-extras-browser.mjs` проверяет выбор и очистку на четырёх площадках, множественный выбор, `false` и итоговую подготовку через настоящий бэк без открытия площадок.

Укрупнённый вариант площадки не создаёт лишний цвет в общей форме: Серый и Серебристый — отдельные точные общие цвета, оба указывают на Kufar «Серый / серебристый», но на других площадках сохраняют собственные значения. Аналогично оранжевый, фиолетовый и золотистый используют группы Kufar. Разные числа дверей, виды полного привода, газа и гибрида сохраняются; подробный вариант можно перенести в более широкий, но неизвестную детализацию не придумываем. Валюты не заменяем, города между областями не объединяем.

Маппинг может содержать `assignments` для составного выбора. Робот/вариатор на Kufar устанавливают автоматическую коробку и её подтип. Газ и гибрид на Onliner устанавливают базовый двигатель и соответствующий флаг; ABW получает свой укрупнённый тип. Это декларативные серверные соответствия, не логика фронта. ИИ выбирает точный общий ID, отдавая приоритет полному названию перед совпадением отдельного слова в укрупнённом alias. Поле объёма двигателя во фронте имеет шаг 0,1 л; ручной ввод не округляется.

## Распознавание

Исполняемые промпты находятся в `CarAiService` и `CarPhotoRecognitionService`; общие правила вариантов — в `CarCandidatePolicy.RULES`. Текст и изображения являются данными, а не инструкциями. Без доказательств неизвестное поле пропускается. Исключение — предложение поколения по косвенным признакам, с явной пометкой для проверки. Родитель сам по себе не доказывает потомка. По внешности нельзя утверждать VIN, пробег, цену или скрытую комплектацию конкретного экземпляра. Возможные характеристики модели допустимы только как явно обозначенные гипотезы; неполный или необоснованный набор не должен сужать список.

После добавления фото появляется кнопка «Распознать с ИИ». POST recognize-photos принимает все JPEG/PNG data URI из images, без ограничения количества в автомобильной форме, компоновщике и автомобильном контракте расширения. Фронт последовательно оптимизирует исходные файлы (включая WebP) до JPEG, чтобы большой набор не декодировался одновременно. Технический предел HTTP-загрузки — 50 МБ; пакет расширения ограничен 50 000 000 символами JSON. Ограничения самих площадок не отменяются. Лимит 12 фото для недвижимости этим изменением не затронут.

Первый этап: CarPhotoComposer/JpegCarPhotoComposer собирает все снимки в один пронумерованный коллаж, четыре ячейки в ряд, порядок слева направо и сверху вниз. Пустые ячейки последнего ряда не считаются фото. Кадры не обрезаются. Рабочая площадь ограничивается уменьшением ячеек при росте набора, без исключения снимков. Каждый отправляемый JPEG строго меньше 512000 байт; base64-транспорт больше. Это размер файла, а не разрешение в пикселях и не лимит токенов.

ИИ возвращает предварительные text, generationHint, observations, candidates, candidateEvidence, warnings и обязательный detailRequests: {single:[8],groups:[[4,1],[2,3]]}. Номера — позиции исходных снимков, начиная с 1. Сервер принимает целые номера и их строковую запись, исключает недоступные номера и повторы между вложениями. Группа из одного оставшегося снимка превращается в single. Если нет ни одного допустимого single, выполняется ровно один компактный запрос выбора по тому же коллажу: выбрать кадр для поколения и все кадры приборной панели/одометра. При повторно некорректном выборе возвращается ошибка без цикла повторов. Все исходники вместо выбранных кадров никогда автоматически не отправляются. В observations собираются признаки и основания; ограничения не дописываются в пользовательский текст объявления.

Второй этап: запрошенные single подготавливаются как целые отдельные кадры с сохранением пропорций; groups — как отдельные коллажи. Каждый файл снова меньше 512000 байт. Все уточнения уходят одним запросом вместе с предварительной информацией и манифестом соответствия вложений исходным номерам. Нумерация ячеек внутри группы локальная; массив photos в манифесте задаёт её соответствие исходным снимкам. ИИ объединяет сведения обоих этапов, исправляет догадки и возвращает окончательное определение. Дополнительного цикла запросов нет. Первый элемент single обязателен: ИИ выбирает наиболее информативный исходный кадр для проверки поколения и рестайлинга, даже при уверенном ответе или единственном фото. План без отдельного кадра требует описанного выше запроса выбора; предварительное описание не заменяет заключительный этап. Остальные single включают кадры одометра; один снимок не дублируется. Если признаков всё равно недостаточно, точное поколение не утверждается в объявлении. При ошибке уточнения предварительное описание не выдаётся за окончательный результат.

Ответ API содержит итоговые text, generationHint, observations, candidates, candidateEvidence, warnings, recognitionPasses (2, либо 3 при исправлении выбора), collage и detailImages с номерами и размерами вложений. Только text помещается в «Распознано ИИ». Служебные наблюдения и ограничения отдельно передаются в последующий POST analyze вместе с description и recognizedText, без фото. Он заполняет поля с приоритетом пользовательских сведений. Полное дерево моделей, поколений и UUID в AI не передаётся; используется существующее компактное описание опций и локальное сопоставление. Итого кнопка выполняет два vision-вызова и один текстовый вызов, всего три при обычном успешном выполнении всей цепочки; при исправлении выбора фото добавляется один vision-вызов. Повторное «Заполнить с ИИ» отправляет только текст. Изменение любого снимка, включая седьмой и последующие, делает ожидаемый ответ устаревшим. При ошибке последующего заполнения итоговый текст распознавания и одиночные кандидаты остаются для повторной попытки. Proxy timeout — 180 секунд: до трёх последовательных vision-вызовов по 45 секунд с подготовкой изображений.

Компактный контракт текстового AI: `facts:[{field:"car.brand",value:"Kia",evidence:"Kia Rio"},{field:"car.year",value:2021,evidence:"2021 года"}]`. Значение и основание находятся в одной записи, включая марку/модель/поколение и географию. Адаптер бэка превращает факты в публичные `values` и `evidence`; отсутствие основания больше не приводит к молчаливому пропуску — есть предупреждение. Сервер получает общий ID «IV Рестайлинг» по alias `(FB) Рестайлинг`; перед точным сопоставлением может убрать префикс уже выбранной марки/модели: `Kia Rio IV рестайлинг` → `IV рестайлинг`. Если соответствие отсутствует или неоднозначно, сохраняется последний однозначный родитель и возвращается предупреждение. Год может использоваться вместе с другими признаками для догадки о поколении, но не превращает её в подтверждённый факт. AI не получает UUID, дерево каталога, aliases или маппинги площадок. Плоские поля передаются как пары `["transmission:Автоматическая", "Автоматическая"]`; Код содержит название, чтобы не путать соседние варианты по номеру; он проверяется по словарю текущего запроса и не заменяет постоянный общий ID. Ответ с чужим кодом не принимается.

`candidates` могут ограничивать только год выпуска, кузов, двигатель, привод, коробку, цвет, места и материал/цвет салона. Backend проверяет каждый код и основание; неизвестный или чужой ID отклоняет весь набор поля. Подтверждённое плоское значение также создаёт ограничение из одного варианта. Если текстовый AI не повторил ранее проверенное ограничение фото, оно сохраняется; при явном уточнении свойства приоритет имеет новый факт. При смене автомобиля AI возвращает `discardPhotoCandidates:true`. Единственный допустимый кандидат автоматически выбирается сразу после «Распознать с ИИ», а также после «Заполнить с ИИ». Автовыбор выполняется, если поле пустое или его прежнее значение назначил AI. Ручной выбор сохраняется. Несколько кандидатов никогда не выбирают один вариант автоматически. При расширении или сбросе ограничения прежний автоматический выбор только по этому ограничению очищается; подтверждённые текстовые факты и ручные значения сохраняются. Фронт фильтрует списки и даёт кнопку «Все варианты». Редактирование исходных текстов снимает видимые ограничения; скрытые данные фото сохраняются при дополнении пользовательского описания, но сбрасываются при редактировании распознанного текста, смене автомобиля или фото. Замена фото удаляет только неизменённый автоматически полученный текст; ручная редакция сохраняется.

При повторном заполнении можно обновлять значения предыдущего AI, если пользователь их не менял; исчезнувшие из нового ответа старые AI-значения очищаются. Ручные значения (включая 0) сохраняются. Пустое числовое поле с `null` заполняется. Уже выбранный вручную родитель не блокирует заполнение пустых потомков той же ветви. Устаревший ответ не перезаписывает изменённые данные. Служебные ограничения не добавляются в описание объявления.

При распознавании текста AI обязательно формирует `car.description` как короткое объявление для покупателя: представление автомобиля, подтверждённые особенности и условия продажи, приглашение связаться. Технические параметры полностью извлекаются в отдельные факты, но не дублируются перечнем в описании. Марку и модель можно назвать; другие характеристики упоминаются только по смыслу. Нельзя придумывать состояние, обслуживание, отсутствие ДТП, торг или преимущества. При скудном источнике текст остаётся коротким. Например, из «Kia Rio 2021, 1.6, автомат, 60000 км. Один владелец, есть сервисная книжка» получается «Продаю Kia Rio. Один владелец, есть сервисная книжка. Свяжитесь со мной, чтобы узнать подробности», а все технические значения идут в поля карточки. Дополнительного AI-запроса для этого нет.

Если AI не вернул `car.description`, сервер объединяет только два исходных текста, без `photoAnalysis`. При превышении лимита 15000 символов сокращает копию для поля и возвращает предупреждение; исходные тексты в форме сохраняются.

Сгенерированное описание не обязано быть дословной цитатой; отсутствие evidence у него не отменяет готовый текст. Для технических фактов evidence остаётся обязательным. Неподтверждённые оценки «в хорошем/отличном/идеальном/безупречном состоянии» удаляются из описания с предупреждением. Прямые цитаты пользователя с конкретным значением сужают служебные фото-варианты; гипотеза без такой цитаты не становится подтверждённым фактом.

Если распознан город без области, сервер восстанавливает его родителя только при единственном совпадении в справочнике. Для Минска в Kufar задан отдельный путь: общий город Минск → регион Минск площадки, с просьбой выбрать район вручную. Это явное отличие структуры площадки, не глобальное объединение ID. Имя продавца Onliner переносится после выбора частного продавца, который является исследованной ветвью подачи.

Уточнение фотографий не получает предварительные числовые утверждения о пробеге из текста и observations обзорного этапа. Модель должна заново прочитать одометр по целому кадру; закрытые рулём или неразборчивые цифры не восстанавливаются.

`AI_MODEL` задаёт текстовую модель, `AI_VISION_MODEL` — модель изображений (по умолчанию `google/gemini-2.5-flash` через существующий OpenRouter). Ключ остаётся серверным. Прямой провайдер DeepSeek не принимает изображения в этом транспорте. `model` в ответе отражает модель соответствующего шага. Для фото разрешён бюджет обдумывания до 1024 токенов в пределах общего лимита ответа 4000; текстовый вызов сохраняет прежний режим. Это не дополнительный запрос, но его токены оплачиваются провайдеру (https://openrouter.ai/docs/guides/best-practices/reasoning-tokens). Локальные тесты используют подставные ответы AI и не расходуют баланс.

## Проверка и ограничения

Стиль распознавания фото: связный текст объявления короткими абзацами, без отчёта или перечня полей, без «предположительно», «вероятно» и подобных вводных слов. Например: «Продаётся Kia Rio в кузове седан, белого цвета». Не добавлять рекламные обещания, цену, пробег, историю обслуживания или исправность по внешнему виду. Обороты «виден», «видно», «на фото», «по снимкам» и аналогичные комментарии о распознавании в объявлении запрещены. Неоднозначные свойства в тексте пропускаются; уточнения и альтернативы остаются в служебных полях. Общий стиль обоих шагов задаёт `CarAiService.AD_STYLE`. Отказ от вводных слов не разрешает утверждать скрытые характеристики как факты. Тот же стиль применяется к пояснениям вариантов и предупреждениям.

Проверяются backend, frontend, extension и браузерный путь с настоящим backend и расширением, но локальными формами площадок: `node scripts/test-cars-browser.mjs`. Тест не публикует объявления и не обращается к площадкам. Его результат нельзя считать проверкой актуального живого DOM.

Проверка только кабинета: `node scripts/test-cars-browser.mjs --editor-only --audit`. Внешний трафик блокируется, страницы площадок не открываются. Используются временные профиль и БД, настоящий собранный frontend/backend; ответы AI и временные сетевые ошибки подставляются тестом. Проверяются фотографии, отдельные шаги AI, ручные значения, зависимые списки, восстановление после ошибок, четыре вкладки недвижимости и узкий экран. Отчёты: `work/cars-browser-tests/result.json` и `audit.json`. Ошибка загрузки вариантов привязана к своему полю и сбрасывается при повторном запросе, не стирая другие ошибки формы.

`scripts/diagnostics/CarAiChainProbe.java` — отдельная запускаемая вручную диагностика настоящих ответов настроенной серверной модели; не использует БД и площадки. Режим `replay` повторно обрабатывает записанные текстовые ответы без вызова AI. Артефакты хранятся в игнорируемой `work/`, могут содержать пользовательские тексты и не коммитятся. Для воспроизведения результатов в production-сборке UI: `node scripts/test-cars-browser.mjs --editor-only --ai-chain=work/chain-verified.json`; для записанного фото-сценария добавить `--photo-directory=<папка шести JPG>`. Проверяется каждое из 23 полей и содержимое всех восьми технических списков, включая передачу скрытых ограничений между операциями. Сверка UI с ответом модели доказывает перенос, но не достоверность знаний модели о заводских комплектациях. Без достаточного основания поле должно оставаться неограниченным; пользователь может вернуть «Все варианты».

AV.by и ABW сохраняют `needs_review` для рецептов без живой проверки. Статические ABW-селекторы имеют отдельное происхождение в `browser-overrides.json` и evidence. Не снимать статус по одному успешному unit-тесту. Список дополнительных полей включает параметры, которые доступны лишь в части состояний формы; неперенесённые поля остаются в отчёте помощника.

ABW: если VIN отсутствует в карточке и видимое поле VIN пустое, помощник один раз нажимает точную кнопку «Заполнить вручную». Введённый пользователем VIN и защищённые от изменения элементы сохраняются. AV.by: перед появлением полей помощник один раз выбирает «Автомобиль с пробегом», не выбирая новый автомобиль. Это вход в форму, а не подтверждение объявления. Onliner: после выбора марки/модели радиокнопки исчезают; результат дополнительно проверяется по точному названию в соответствующей позиции заголовка технического шага. Следующая зависимость заполняется только после подтверждения выбора.

Приёмка живого переноса: по одному авторизованному объявлению на каждой площадке, сверка каждого заданного значения, зависимости и пустых необязательных полей, успешные серверные превью фото, смена марки/модели, повторный запуск после остановки и reload без заполнения. Кнопки окончательной отправки, продвижения и промежуточных шагов пользователь нажимает самостоятельно. До такой проверки нельзя объявлять всю интеграцию четырёх площадок полностью проверенной.

Поколение: фото возвращает скрытую generationHint (марка, модель, лучшая догадка и основание). Она передаётся текстовому AI без дополнительного запроса и не дописывается в объявление. При «Заполнить с ИИ» модель может вернуть факт поколения с inferred:true; бэк сопоставляет его внутри выбранной модели и показывает просьбу проверить выбор. Для одного кода кузова допускается частичное совпадение с полным названием/alias: G12 → G12 (Long), F22 → F22 / F23, 8Z → I (8Z). Точный вариант приоритетен; затем предпочтение конкретному названию перед широким alias. Совпадает целый код, а не его префикс (G1 ≠ G12). Если несколько вариантов имеют одинаковый приоритет, автоматического выбора нет. Без указания рестайлинга частичное сопоставление предлагает базовое поколение и требует проверки. Ручной выбор сохраняется; после фото поколение заполняется автоматически через тот же текстовый анализ и локальное сопоставление справочника.

Год выпуска в редакторе — список по убыванию от текущего года (2026 при внедрении) до 1886. В карточке и маппингах остаётся целым числом; сервер выдаёт варианты с текстовыми ключами годов. В AI-промпте передаётся только диапазон min/max, candidates для года содержит сами годы, не UUID. Неизвестный диапазон не ограничивает список; одиночный подтверждённый год выбирается, несколько годов остаются на выбор. Явный год из пользовательского текста приоритетнее диапазона по фото.

ABW: по указанию пользователя промежуточная кнопка «Продолжить» после характеристик нажимается скриптом. Проверенный селектор: .adverts-form > button[type="button"], точный текст «Продолжить» и наличие заголовков Марка/Модель/Год выпуска. Переход разрешён после стабильного прохода заполнения, только для единственной доступной кнопки. Ошибка валидации не вызывает цикл кликов: повтор возможен после изменения данных. Другие шаги, окончательная публикация и продвижение автоматически не подтверждаются. Живой DOM прочитан без нажатия и без перезагрузки страницы.
