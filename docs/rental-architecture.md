# Архитектура модуля «Аренда квартир»

Одна карточка квартиры → сервер готовит значения для выбранных площадок → расширение
заполняет их формы. Правила площадок — в данных и только на сервере; кабинет и расширение
показывают и исполняют его ответ. Модуль объявлений на эту архитектуру не переведён.

## Справочники

`data/rental/apartments_long_term_rent/` едет в релиз вместе с кодом (`RENTAL_REFERENCE_DIR`),
читается только через `manifest.json` (`format_version: 1`, `source_schema_version: "1.2"`):

- common — поля карточки (понятия, типы); `card.json` — версия модели (2), названия площадок,
  варианты `canonicalValues`, подписи, контакты профиля, адресная проекция, «Рядом с домом»;
- на площадку: исходная схема (поля формы, коды, `when`), план `runtime/preparation_<id>.json`
  (карточка → нативное поле, константы, адрес, проверки, `transfer: manual` с причиной) и
  рецепт `runtime/browser_<id>.json` (URL, `ready`, контролы, шаги). Исследования — в `research/`.

Комплект читается один раз при старте и разбирается в неизменяемые records `rental/model`
(Jackson databind, `Json.TYPED`: неизвестный ключ и значение другого JSON-типа — ошибка с путём
в файле; исходные схемы и common хранят и исследовательские факты, читаются только нужные).
Затем `ReferenceValidator` и `BrowserRecipeValidator` проверяют ссылки между файлами, коды,
условия, циклы, ключи каждого действия и шага, а покрытие — что каждое поле плана заполняет
контрол, оно `manual` с причиной, `deferred` или константа (иначе `prepared_only` — отказ).
Битый комплект — приложение не стартует, в логе файл и причина (`ReferenceBundleException`).
Валидатор: `--validate-rental-reference=<каталог>`, таблица покрытия: `--rental-coverage=<каталог>`.

Две версии — SHA-256 файлов как написаны: `cardVersion` (common + card.json) хранит карточка,
сравнивают проверка, ИИ и публикация (иначе 409 «Правила обновились», «Обновить поля карточки»);
`integrationVersion` (manifest, схемы, планы, рецепты) получает только расширение.

## Сервер (`backend/src/main/java/by/autopost/rental/`)

| Пакет | Что делает |
|---|---|
| `model` | Records: `Schema`/`FieldDef`/`Choice`, `Condition` (sealed, три исхода), `Mapping`/`MappingRule`, `Conversion` (sealed: identity, lookup, list/multi lookup, decimal, phone, plain_text_html, files), `FormRecipe`, `CardModel`, `Card`, `Address`, `Value`; `CardFields` — ID полей, которые читает код, единицы и роли |
| `catalog` | Чтение и разбор файлов, проверки, `ReferenceSnapshot` (один неизменяемый комплект на релиз) |
| `engine` | `PreparationEngine` (константы, строки плана по зависимостям, адрес, проверки схемы с применимостью каждого поля), `CardChecks` (значения из адреса, этаж, прежние значения), покрытие |
| `application` | Сценарии: схема редактора, состояние полей, проверка, запуск, черновики, фото, публикации; DTO ответов |
| `persistence` | SQLite/JDBC по кабинету и ожидаемой ревизии; разовая миграция хранимых карточек |
| `web` | Контроллеры: JSON входа → `Card`, документ карточки хранится как написан |
| `ai`, `address` | ИИ-заполнение с цитатами (`AiCard` из комплекта), DaData вне блокировок |

`JsonNode` остаётся только на границах: чтение файлов комплекта, тела запросов и копия документа
в `normalize`, хранимые документы прежних форматов (миграция), ответы ИИ и DaData. ArchUnit
(`RentalLayersTest`) запрещает его в `model`, `engine`, `application`.

API редактора (`/api/workspace/rental/…`):

- `GET editor` — группы полей карточки (`id`, `name`, `type`, `unit`, `role`), `card` (подписи,
  «Рядом с домом», `addressFields`, контакты профиля), названия площадок и их полей, `cardVersion`;
  ни одного правила площадки;
- `POST fields {draft}` — какие поля показать для этой карточки и выбранных площадок: поле без
  площадок видно всегда; поле площадки — если площадка выбрана и её нативное поле применимо по
  подготовке (или ещё неизвестно); `required`, `transferred` (форма получает значение) и `choices`;
- `POST prepare {id, draft}` — по площадке `values`, `issues` (с `source` для «Уточнить»),
  `form` и `manual` (текст значения, как его покажет проверка; причина), `checksPassed`; фото
  считаются по карточке на сервере; непустое поле `manual` выключает автоподачу;
- `POST extension-config {id, draft}` — для сохранённой ревизии задания расширению: рецепт с
  заполненными контролами, `unbound`, `checksPassed`, запись публикации, фото карточки;
- черновики (`drafts`, ревизии, 409), фото (`drafts/{id}/photos…`), публикации
  (`publications/{id}`, `…/link`), `normalize`, `analyze`, адреса.

Хранение: `rental_drafts` (документ, заголовок и адрес колонками), `rental_photos` (до 12,
JPG/PNG/WebP), `rental_publications` (запуск = ревизия + `integrationVersion` + площадка, статусы
`opened`/`filled`/`submitted`/`needs_action`/`stopped`, переходы решает сервер, ссылка вводится
в «Мои квартиры»). Карточки модели 1 переводит `--migrate-rental-drafts` при выкладке.

## Кабинет (`frontend/src/app/rental/`)

Аренда — маршрут `#/rental` (`app.routes.ts`, hash location: nginx отдаёт одну страницу);
`RentalPageComponent` берёт кабинет и контакты из `RentalSession`, уход с маршрута и выход
сохраняют набранное. `RentalEditorComponent` создаёт свою сессию `RentalDraftStore`: состояние
в signals, автосохранение, очередь записей, ревизии, фото; `RentalFieldStates` и `RentalCardCheck`
запрашивают поля и проверку после паузы (переключение площадки — сразу) и держат последний
ответ. `RentalViewModel` — computed-списки того, что рисовать; правил площадок в браузере нет.
Транспорт — `RentalApi` на `HttpClient` с `rentalInterceptor` (заголовок кабинета, ошибки
сервера и прокси). ID полей, которые читает кабинет, — `card-fields.generated.ts` из `CardFields`
(`node scripts/rental-card-fields.mjs`; `npm test` проверяет совпадение).

Правка адреса сбрасывает `addressFields`; «Рядом с домом» — только при смене подтверждённого
дома или очистке, с кнопкой «Вернуть». ИИ предлагает факты с цитатой и не затирает ручные.

## Расширение (0.9.6)

`rental-core/background/form/page/autocomplete` исполняют рецепт из `extension-config`: без
кода из JSON, вкладка и кабинет привязаны к заданию, адрес подтверждается только единственным
совпадением подсказки. По умолчанию — помощник; финальную кнопку (пока только Kufar) нажимает
только автоматический режим с подтверждением при `checksPassed: true`, перед кликом сервер
принимает `submitted` для той же ревизии и правил. Статусы и CAPTCHA/вход — пользователю.

## Новая площадка и проверки

Площадка = схема + план + рецепт в комплекте + запись в manifest и card.json; домен формы
и стартовый URL — релиз расширения. Комплект проверяет валидатор; «JSON прошёл валидатор» не
значит, что форма заполняется — живая проверка в режиме помощника обязательна.

Тесты: `npm test` (расширение, границы кабинета), `npm run test:frontend`, `npm run
test:backend` (комплект, покрытие, движок, HTTP-контракт, миграция, фото, публикации, ArchUnit).
