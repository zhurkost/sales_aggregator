# Архитектура карточки долгосрочной аренды

Область этого документа — модуль аренды Angular/Spring. Старые автомобильные,
товарные и расширенческие модули не объявляются переведёнными на эту архитектуру.
Главный инвариант: один пользовательский факт хранится в общей карточке и
преобразуется в требования выбранных площадок. Нативные идентификаторы площадок
не становятся идентификаторами общих полей.

## Передача в браузер (расширение 0.9.5)

`manifest.platforms.<id>.browser` подключает `runtime/browser_<id>.json` — рецепт
текущей формы, обязательный для каждой площадки; исследовательские `bindings_*.json`
лежат в `research/` и не исполняются. Рецепт содержит URL формы, признаки выбранной категории (`ready`),
входные шаги, селекторы и действия, адресные поисковые части, зависимости `after`,
переходы и проверенные кнопки подачи. Идентификаторы полей проверяются по исходной
схеме, ключи — по списку того, что читает расширение; изменения меняют
`integrationVersion`. Никакой JavaScript из JSON не исполняется.

`RentalPublicationService` сверяет карточку с сохранённой версией в текущем
кабинете. `RentalBrowserPreparation` собирает только заполненные нативные значения
и необходимые инструкции и добавляет в каждое задание `checksPassed` подготовки этой
площадки (нет замечаний) и `unbound` — названия полей «вручную» из покрытия.
`checksPassed` и замечания проверки **не запрещают запуск**.

## Покрытие «подготовлено → заполнено»

При загрузке комплекта для каждой площадки вычисляется `PlatformCoverage` (records
`CoverageRow`, `Transfer`): каждое поле плана (строки, адресные части, координаты,
константы, `deferred_fields`) → поля карточки → нативное поле → контрол рецепта →
статус `transferred` (заполняет контрол), `manual` (в строке плана
`"transfer": "manual"` и `manual_reason`), `deferred` (адрес и поля аккаунта, которые
план не готовит; причина из `deferred_fields`), `constant`. Поле, подготовленное из
карточки без контрола и без пометки (`prepared_only`), и пометка `manual` у поля с
контролом отклоняют комплект с именем файла плана. `--rental-coverage=<комплект>`
печатает покрытие markdown-таблицей.

`prepare` по каждой площадке отдаёт `form` (что заполнит расширение, включая адрес),
`manual` (что ввести на площадке, с причиной), `issues` и `checksPassed`. Кабинет
показывает «Уйдёт в форму: N полей · Вручную на площадке: M» и не пишет
«Подготовлено», если есть поля «вручную». У каждого использования поля карточки
в схеме редактора есть `transferred` (форма этой площадки получает значение или оно
нужно заполняемому полю); поле, которое не получает ни одна выбранная площадка,
помечено «пока не переносится».
Поисковая строка адреса передаётся отдельно от внутренних кодов площадки: расширение
подтверждает только единственное точное совпадение в подсказках.

Angular-компонент `RentalPublicationComponent` отвечает за запуск и прогресс,
`RentalPublicationGateway` — за границу с расширением и локальными фото.
Состояние проверки `RentalCardCheck` независимо от автосохранения: предыдущий
отчёт остаётся на месте и обновляется после паузы. Контакты из `card.profileDefaults`
подставляются только в отсутствующие поля; явно очищенное или изменённое значение
не затирается. Город профиля не подставляется вместо адреса сдаваемой квартиры.

Расширение использует отдельные `rental-core`, `rental-background`, `rental-form`
и `rental-page`. Действие `iframe_richtext` вставляет текст в тело редактора внутри
iframe того же происхождения (TinyMCE описания Realt) так же, как `richtext`. Задание ограничено origin Автопоста, кабинетом, карточкой и
конкретной вкладкой площадки. Запуск — это ревизия карточки и `integrationVersion`:
повторный запуск той же пары возвращает существующие задания, та же ревизия при
новых правилах — новый запуск. Перед окончательной отправкой обе сверяются с
текущим `extension-config`; кабинет требует возможности `rental-checks-passed`,
`rental-integration-version` и `rental-iframe-richtext`.
Оплата, CAPTCHA и нераспознанные этапы передаются пользователю. Статус публикации
не выводится из одного клика или исчезновения формы.

Исследованы формы Kufar, r.onliner.by, Realt и Domovita 2 ноября 2026 года.
Поддержаны наблюдавшиеся основные поля, перечисления, фото и известные переходы.
Полный живой проход с настоящей публикацией не выполнялся. У Onliner, Realt и
Domovita финальная отправка пока остаётся ручной (`submit: []`); Kufar допускает
одну попытку подачи после проверки отсутствия платного итога. По умолчанию запуск
идёт в режиме помощника. Финальный клик возможен, только если пользователь включил
автоматический режим с подтверждением и у задания площадки `checksPassed: true`;
отсутствующее поле считается `false`. Поля «вручную» показываются явно. Все специфические поля, адресные подсказки и закрытые ветви
нельзя считать полностью покрытыми только по наличию JSON-схемы.

Фото: до 12 за запуск, сжатие до 1600 px, JPG; исходный выбор хранится в IndexedDB
этого браузера по кабинету/карточке. В расширение передаются бинарные данные, на
endpoint справочника они не отправляются. URL из текстового поля вложений не
скачиваются автоматически. Задания и фото расширения живут два часа; после
перезапуска браузера задания нужно запустить снова. Это ещё не серверная история
публикаций и не подтверждение модерации.

## Сервер

Пакеты находятся в `backend/src/main/java/by/autopost/rental/`:

| Пакет | Ответственность |
|---|---|
| `web` | Авторизация запросов и вызов прикладного сервиса. Без SQL, чтения файлов и обращения к ИИ |
| `application` | Сценарии редактора, подготовка карточки, сохранение/открытие/удаление черновика; порт `RentalDraftRepository` |
| `persistence` | SQLite/JDBC, запросы с обязательным workspace, атомарная проверка ожидаемой ревизии; команда `--migrate-rental-drafts` |
| `catalog` | Загрузка комплекта через `manifest.json` при старте и его проверка, снимок на операцию, версии, сборка схемы редактора |
| `model` | Типизированные значения, условия с тремя исходами, обход полей; без Spring, сети и диска |
| `preparation` | Исполнение известных преобразований, адресная подготовка, проверки значений и результаты |
| `card` | Разовая миграция карточек модели 1 с сохранением неоднозначных значений в `legacy`, проекция единого адреса |
| `ai` | Подготовка запроса из текущей схемы и проверка предложенных фактов, цитат и конфликтов |
| `address` | Поиск и подтверждение адреса DaData: `DadataClient` (HTTP), `AddressService` (кэши, лимиты) |

Общий `by.autopost.ai.AiGateway` владеет HTTP-клиентом, серверным ключом и лимитом
запросов. Контроллер аренды не вызывает другой контроллер. `shared` содержит
только общие JSON/текстовые функции, хеширование и исключение API.

Комплект читается и проверяется один раз, при запуске приложения
(`FileReferenceRepository`). Битый или отсутствующий комплект — приложение не
стартует, в логе путь файла и причина (`ReferenceBundleException`); во время работы
файлы не перечитываются: новый комплект — новый релиз. `RentalCatalog` получает
один `ReferenceSnapshot` на операцию: каждая часть копируется в нём один раз, при
первом обращении, поэтому правки одной операции не доходят ни до загруженного
комплекта, ни до других операций.

Две версии комплекта, обе — SHA-256 при загрузке:

- `cardVersion` — common и `card.json`, то есть то, что карточка видит и хранит.
  Редактор получает его в схеме, карточка хранит тот, под которым её редактировали;
  `prepare`, `analyze` и публикация с другим значением отвечают 409 «Правила
  обновились», «Обновить поля карточки» (`normalize`) ставит текущий. Сохранение
  версию не сравнивает: правки не теряются, а в подготовку карточка уходит только
  после обновления полей.
- `integrationVersion` — manifest, исходные схемы, планы и рецепты браузера: как
  карточка попадает в формы. Приходит только в `extension-config`; правка селектора
  или плана меняет лишь её, открытые редакторы продолжают сохранять и проверять.

Черновики хранятся отдельно в `rental_drafts`; заголовок и адрес для списка лежат
в колонках `title` и `address_label`, список не разбирает JSON карточки. Размер
карточки ограничен одной константой `RentalController.CARD_CHARACTERS` (413).
Все запросы ограничены кабинетом.
Обновление и удаление выполняются по ожидаемой ревизии; позднее сохранение не
воссоздаёт удалённую запись. Открытие возвращает карточку как сохранена и не
зависит от комплекта; подготовка к площадкам требует исправного комплекта.

Карточка хранит `modelVersion` (модель 2, её же задаёт `card.json`). Карточки
модели 1 переводятся один раз командой
`java -jar autopost-api.jar --migrate-rental-drafts --database=<workspace.sqlite> --rental-reference=<комплект>`;
её запускает `deploy/spring/deploy-release.sh` после резервной копии и до
переключения релиза. Она же переносит карточки модели 2, сохранённые с прежним
`schemaVersion` (хеш всех правил), на `cardVersion` комплекта релиза. Команда пишет
каждую карточку с ожидаемой ревизией (+1), не трогает текущие и печатает отчёт: сколько карточек, сколько переведено, сколько
неоднозначных значений осталось в `legacy`. Открытие, проверка и публикация
карточки модели 1 дают 409 «Карточку нужно перенести командой миграции.»; блок
«Сверьте прежние сведения» появляется только при непустом `legacy`. В модели 2
нет `extras`: все факты лежат в `values`.

## Файлы и границы контрактов

Рабочие справочники находятся в GitHub: **`data/rental/apartments_long_term_rent/`**.
Это источник версии для разработки, CI и сервера. Каталог включается в архив
релиза; сервер читает его через `RENTAL_REFERENCE_DIR`. Локальный запуск подключает
его автоматически. В Angular assets справочники не копируются. Отдельный
искусственный пример остаётся в `backend/src/test/resources/reference-example/`.

Это разные виды данных:

1. **Исходная схема площадки** — поля, типы, варианты, ограничения, `when`.
2. **Common** — общие поля Автопоста. Одинаковые факты не дублируются по площадкам.
3. **Mapping / план подготовки** — связи common → нативное поле, точные коды,
   разрешённые преобразования, зависимости подготовки, константы и ограничения.
4. **Рецепт браузера** (`runtime/browser_*.json`) — URL формы, селекторы, действия,
   порядок заполнения и переходы. Не содержит бизнес-преобразований.
5. **Card** — модель карточки, названия площадок, общие варианты, подписи,
   контакты профиля, адресная проекция и сведения «Рядом с домом».

Исследования — отчёты, исследовательские маппинги и bindings, задания —
лежат в `research/rental/apartments_long_term_rent/<id>/`; сервер их не читает.

Исследовательский mapping этапа B и исполняемый план сейчас различаются:
`research/rental/apartments_long_term_rent/<id>/mapping_*.json` сохраняет результат исследования;
**активный runtime-источник — `runtime/preparation_*.json`**, указанный в manifest.
Он содержит только проверенные преобразования поддерживаемого исполнителя.
Изменение исследовательского mapping само по себе не активирует новые правила.
Переход к новому плану — отдельное обновление комплекта, которое проходит
валидатор. Не следует одновременно редактировать оба файла как независимые
рабочие настройки.

Комплект читается только через `manifest.json`: `format_version: 1`,
`source_schema_version: "1.2"`, `category_id`, пути `common`, `card` и реестр
`platforms`; у площадки — пути `schema`, `plan` и `browser`.
Другой формат исходных схем не принимается: факты поля лежат в `fill_rule`.
Пути относительные, выход за каталог запрещён. Размер каждого JSON ограничен 5 МиБ.
Пример — в тестовом комплекте.

Для этого редактора комплект должен содержать одну конечную категорию:
подкатегории нельзя молча склеивать или наследовать. Общий файл и схемы площадок
не заменяются догадками ИИ при запуске сервера.

Проверяются версии, уникальность ID, ссылки на common и
нативные поля, известные виды преобразований, условия, циклы зависимостей и
минимальный контракт `ready`. У manifest, `card.json`, планов (строк,
преобразований каждого вида, пар значений) и рецептов (полей по виду действия,
`autocomplete`, шагов) есть явный список ключей с проверкой типа: неизвестный ключ
отклоняет комплект с указанием места. Это проверка
структуры, **не подтверждение работоспособности внешней формы**. Принятие файлов,
адресные справочники, неизвестные ограничения и неподдержанные действия требуют
проверки конкретного адаптера. `publicationReady` остаётся false.

## Адрес из описания

`RentalAiPolicy` принимает только адресную цитату из описания. `LiteralAddress`
выделяет её части и проверяет буквальное происхождение частей, предложенных ИИ.
Идентификаторы, координаты и признак подтверждения от ИИ не принимаются.
`RentalAiAddressResolver` вызывает `rental.address.AddressService` в контексте
кабинета: поиск, сопоставление города/типа улицы/дома/корпуса и подтверждение
единственного совпадения. Запрос к DaData идёт вне блокировок; ответы кэшируются
по запросу для всех кабинетов, ID подсказок привязаны к кабинету. В DaData передаётся адресная цитата, не всё описание.
При отсутствии совпадения, неоднозначности или сбое сохраняются распознанные
части с `provider: manual` и причиной в `resolution`; Angular открывает ручные
поля. Остальные предложения ИИ продолжают работать. Старую карточку с одной
строкой адреса можно дополнить повторным заполнением с ИИ; ручные изменения
сначала предлагаются к подтверждению. Расширение получает ту же структуру
`address`, что и после ручного выбора подсказки. Для последовательных запросов
ИИ и DaData таймаут прокси составляет 90 секунд.

## Angular

Файлы находятся в `frontend/src/app/rental/`:

- `rental-models.ts` — типы DTO; `rental-api.ts` — единственная функция транспорта.
- `RentalDraftStore` — отдельный экземпляр на редактор: автосохранение, очередь
  записей, ревизии, открытие/удаление, загрузка схемы и подготовка.
- `RentalAiAssistant` — запрос предложений, защита от позднего ответа, принятие
  отдельных замен. Использует состояние карточки; не обращается к DOM.
- `RentalViewModel` — применимость полей, подписи, фильтрация и объединённые ошибки;
  не сохраняет и не делает сетевых запросов.
- `RentalEditorComponent` — координация пользовательских событий, явное изменение
  полей, навигация и фокус. Шаблон обращается к `store`, `ai` и `view` напрямую.
- `RentalFieldsComponent`, `AddressInputComponent`, `RentalSavedListComponent`,
  `RentalAiReviewComponent` — отдельные элементы интерфейса. Поиск адресов имеет
  собственный жизненный цикл; отображение списка и предложений ИИ не владеет API.

Состояние не является глобальным singleton: смена кабинета или уничтожение
редактора не переносит карточку в другую сессию.

Любая правка адреса сбрасывает координаты и адресные части в `values`. Сведения «Рядом
с домом» (`card.addressDependentFacts`) сбрасываются только при смене подтверждённого
дома на другой подтверждённый дом или при очистке адреса; ввод в поиск и ручные части
адреса их не трогают. Принятие адреса от ИИ идёт по тем же правилам. Сброс можно
отменить кнопкой «Вернуть» до следующего изменения адреса.

## Подключение и обновление площадки

Для адресных подсказок `runtime/browser_*.json` задаёт `autocomplete`: область
поиска `scopeSelector`, элементы `optionSelector`, текст `labelSelector`, признак
загрузки `busySelector`, вид адреса `kind` и подтверждение `value-and-closed`.
`contextParts` (`region`, `district`) и `contextSelector` позволяют различить
одноимённые населённые пункты. Сервер подставляет в `matchContext` только компоненты
адреса текущей карточки. Нативные коды других адресных сервисов не используются.
Отдельный `extension/rental-autocomplete.js` обрабатывает эти декларативные правила:
сохраняет фокус, сопоставляет название и тип, ждёт стабильный единственный вариант,
затем проверяет выбранный текст и закрытие списка. Зависимость `after` разрешает
следующее поле только после подтверждения предыдущего. Разметка Realt проверена
03.11.2026, автоматический обработчик — на воспроизведённой DOM-структуре.
Необязательный `selectedClass` у контрола или шага — фрагмент класса, которым
площадка отмечает выбранный вариант-кнопку: у Kufar `chip__filled-green` (тот же
класс проверяет `ready`), у Realt `text-white`.

1. Этап A по актуальным `parsing_rule.txt` и `parsing_format_rule.txt`: получить
   исходную схему и binding с доказательствами. Не менять `parsing_input.txt`.
2. Отдельный этап B: сопоставить семантику полей/вариантов с существующим common.
   Добавлять новый общий факт лишь если соответствующего ещё нет.
3. Собрать план подготовки из поддерживаемых обработчиков, явно сохранить
   неизвестные ветви для проверки. Добавить площадку в manifest и card.
4. Обновить комплект в Git и включить изменения в PR. Сырые доказательства, HAR
   и сессии сохранять отдельно. Хешей в планах нет: согласованность плана со
   схемой и common (ссылки на поля, коды, типы) проверяет валидатор.
5. Проверить комплект без запуска сервера:

   ```sh
   java -jar backend/target/autopost-api.jar --validate-rental-reference=data/rental/apartments_long_term_rent
   ```

6. Выполнить контрактные тесты, подготовку вымышленной карточки и проверку
   разрешённых ветвей внешней формы. Подключение нового вида browser-действия
   требует кода адаптера и проверки, одного JSON недостаточно.
7. Собрать релиз: упаковка проверяет и включает комплект из Git. Развёртывание
   устанавливает `RENTAL_REFERENCE_DIR=/opt/autopost/current/data/rental/apartments_long_term_rent`
   и переключает приложение со справочниками вместе. Сохранять предыдущий релиз,
   конфигурацию и базу для отката. Не редактировать файлы на сервере: работающее
   приложение их не перечитывает, битый комплект не даст ему стартовать.

Новая площадка с уже поддержанными типами и преобразованиями подключается
данными. Пятая искусственная площадка проверяется тестами.
Сайт не предоставляет отдельный API справочников; рабочие JSON доступны команде
в репозитории вместе с исходным кодом.

При проверке действующего набора обнаружено одно неоднозначное название жилого
комплекса Kufar с двумя кодами. Из активного плана удалены оба автоматических
соответствия; исходные схемы и исследовательский mapping сохранены. Название в
карточке остаётся, подготовка сообщает о неподтверждённом соответствии.

## Контроль регрессий

`npm test` включает проверку границ фронтенда; backend `ArchitectureTest` запрещает
SQL вне persistence, HTTP/Servlet в предметных модулях и вшитые ID четырёх площадок.
`ReferenceBundleTest` проверяет формат 1.2, типы кодов, однократное чтение и
изоляцию снимков, какие правки меняют `cardVersion`, а какие `integrationVersion`,
неизвестные ссылки/обработчики/ключи, циклы и пути; `RentalReferenceStartupTest` —
что битый комплект не даёт приложению стартовать; `RentalDraftMigrationTest` —
разовую миграцию карточек; `RentalCoverageTest` — статусы покрытия, отказ комплекта
с неразмеченным полем, команду `--rental-coverage` и 0 `prepared_only` в реальном
комплекте.
Тест также загружает реальный комплект из репозитория и проверяет его согласованность.
Прежние тесты карточек, ИИ, адресов и конкурентного сохранения остаются.

Эти проверки запускаются существующим CI. Полный набор:
`npm test`, `npm run test:frontend`, `npm run build`.
