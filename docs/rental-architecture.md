# Архитектура карточки долгосрочной аренды

Область этого документа — модуль аренды Angular/Spring. Старые автомобильные,
товарные и расширенческие модули не объявляются переведёнными на эту архитектуру.
Главный инвариант: один пользовательский факт хранится в общей карточке и
преобразуется в требования выбранных площадок. Нативные идентификаторы площадок
не становятся идентификаторами общих полей.

## Слои действующего приложения

Проверка 5 ноября 2026 года: кабинет содержит только аренду квартир. Бэкенд —
модульный монолит с тремя основными слоями: HTTP → прикладные сервисы → доступ
к данным через интерфейсы репозиториев. Предметные преобразования карточки
вынесены из этих слоёв в чистые классы. Отдельный интерфейс для каждого сервиса
не требуется: интерфейсы используются на границах хранения и внешних систем.

| Область | Входной слой | Прикладной слой | Хранение / внешний адаптер |
|---|---|---|---|
| Учётная запись | `WorkspaceController`, `Access` | `WorkspaceService` | `WorkspaceRepository` → `JdbcWorkspaceRepository` |
| Квартиры | `RentalController` | `RentalDraftService`, `RentalCatalog`, `RentalPublicationService` | `RentalDraftRepository` → `JdbcRentalDraftRepository`; `ReferenceRepository` → `FileReferenceRepository` |
| Адреса | `RentalController` | `AddressService` | `AddressProvider` → `DadataAddressGateway` |
| ИИ | `RentalAiController` | `RentalAiService`, проверка фактов и адреса | `AiGateway`, адресный сервис |

`Access` отвечает за HTTP-защиту, извлечение cookie и проверку контекста кабинета.
SQL, проверка паролей и выдача сессии находятся за этой границей. Регистрация
профиля и создание сессии выполняются одной транзакцией в `WorkspaceService`;
cookie выставляется контроллером только после успешного завершения сервиса.
Сохранение и удаление квартиры используют транзакции и ожидаемую ревизию.
Транзакции не охватывают сетевые запросы к ИИ или адресному провайдеру; аннотация
не добавляется механически ко всем операциям чтения.

Профили и записи репозитория представлены типизированными record. Карточка и
справочники сохраняют JSON-формат: их состав определяется версионируемой схемой.
Инициализация SQLite остаётся в `Database` и JDBC-репозитории аренды; переход на
инструмент миграций БД в эту проверку не входит. Изменения схемы и удаление
пользовательских данных для разделения слоёв не требуются.

Для Angular используется разделение **компоненты → состояние и правила →
адаптеры API/браузера**. `WorkspaceGateway` и `RentalAddressGateway` скрывают
маршруты API и детали транспорта. `RentalDraftStore` принадлежит экземпляру
редактора, `RentalDraftEditor` изменяет карточку, `RentalViewModel` вычисляет
отображение, а компоненты управляют событиями, фокусом и жизненным циклом.
`RentalPublicationGateway` изолирует расширение и локальное хранилище фото.
Серверные контроллеры и репозитории на фронте не дублируются.

## Передача в браузер (расширение 0.9.7)

`manifest.platforms.<id>.browser` подключает `runtime/browser_<id>.json`.
Это отдельный исполняемый binding для текущих форм; исследовательские
`bindings_*.json` автоматически не исполняются. Browser-файл содержит URL формы,
признаки выбранной категории (`ready`), входные шаги, селекторы и действия,
адресные поисковые части, зависимости `after`, переходы и проверенные кнопки подачи.
Идентификаторы полей проверяются по исходной схеме; изменения входят в отпечаток
комплекта и кэшируются вместе с ним. Никакой JavaScript из JSON не исполняется.

`RentalPublicationService` сверяет карточку с сохранённой версией в текущем
кабинете. `RentalBrowserPreparation` собирает только заполненные нативные значения
и необходимые инструкции. `dataReady` и замечания проверки **не запрещают запуск**.
Поисковая строка адреса передаётся отдельно от внутренних кодов площадки.
Стратегия выбора задаётся browser binding: Kufar выбирает первый результат;
Onliner ищет населённый пункт и выбирает единственный результат либо точное
совпадение без учёта регистра, если вариантов несколько.

Angular-компонент `RentalPublicationComponent` отвечает за запуск и прогресс,
`RentalPublicationGateway` — за границу с расширением и локальными фото.
Состояние проверки `RentalCardCheck` независимо от автосохранения: предыдущий
отчёт остаётся на месте и обновляется после паузы. Контакты из `card.profileDefaults`
подставляются только в отсутствующие поля; явно очищенное или изменённое значение
не затирается. Город профиля не подставляется вместо адреса сдаваемой квартиры.

Расширение использует отдельные `rental-core`, `rental-background`, `rental-form`
и `rental-page`. Задание ограничено origin Автопоста, кабинетом, карточкой и
конкретной вкладкой площадки. Повторный запуск той же ревизии возвращает существующие
задания. Перед окончательной отправкой сохранённая версия сверяется повторно.
Оплата, CAPTCHA и нераспознанные этапы передаются пользователю. Статус публикации
не выводится из одного клика или исчезновения формы.

Исследованы формы Kufar, r.onliner.by, Realt и Domovita 2 ноября 2026 года.
Поддержаны наблюдавшиеся основные поля, перечисления, фото и известные переходы.
Полный живой проход с настоящей публикацией не выполнялся. У Onliner, Realt и
Domovita и Kufar финальная отправка остаётся ручной (`submit: []`). Переход после
заполнения и выбор продвижения выполняет пользователь. Неперенесённые поля
показываются явно. Все специфические поля, адресные подсказки и закрытые ветви
нельзя считать полностью покрытыми только по наличию JSON-схемы.

Фото: до 12 за запуск, сжатие до 1600 px, JPG; исходный выбор хранится в IndexedDB
этого браузера по кабинету/карточке. В расширение передаются бинарные данные, на
endpoint справочника они не отправляются. URL из текстового поля вложений не
скачиваются автоматически. Задания и фото расширения живут два часа; после
перезапуска браузера задания нужно запустить снова. Это ещё не серверная история
публикаций и не подтверждение модерации.

## Сервер

Пакеты находятся в `backend/src/main/java/by/autopost/rental/`:

| Пакет | Ответственность |
|---|---|
| `web` | Авторизация запросов и вызов прикладного сервиса. Без SQL, чтения файлов и обращения к ИИ |
| `application` | Сценарии редактора, подготовка карточки, сохранение/открытие/удаление черновика; порт `RentalDraftRepository` |
| `persistence` | SQLite/JDBC, запросы с обязательным workspace, атомарная проверка ожидаемой ревизии |
| `catalog` | Чтение и проверка версионируемого комплекта, адаптация формата схем, неизменяемый снимок, сборка схемы редактора |
| `model` | Типизированные значения, условия с тремя исходами, обход полей; без Spring, сети и диска |
| `preparation` | Исполнение известных преобразований, адресная подготовка, проверки значений и результаты |
| `card` | Миграция прежних карточек, сохранение неоднозначных значений, проекция единого адреса |
| `ai` | Подготовка запроса из текущей схемы и проверка предложенных фактов, цитат и конфликтов |

Общий `by.autopost.ai.AiGateway` владеет HTTP-клиентом, серверным ключом и лимитом
запросов. Контроллер аренды не вызывает другой контроллер. `shared` содержит
только общие JSON/текстовые функции, хеширование и исключение API.

`RentalCatalog` получает один `ReferenceSnapshot` на операцию. Репозиторий читает
каждый файл при загрузке комплекта один раз, проверяет контрольные суммы и
согласованность, затем кэширует результат. Внешние потребители получают копии
JSON: миграция карточки не меняет общий справочник. Несогласованный комплект
отклоняется, а прежняя схема не подставляется молча.

Черновики хранятся отдельно в `rental_drafts`. Все запросы ограничены кабинетом.
Обновление и удаление выполняются по ожидаемой ревизии; позднее сохранение не
воссоздаёт удалённую запись. При временном отсутствии комплекта сохранённая
карточка доступна для чтения в исходном виде. Подготовка к площадкам требует
исправного комплекта. Разбиение пакетов не требует миграции пользовательских данных.

## Файлы и границы контрактов

Рабочие справочники находятся в GitHub: **`data/rental/apartments_long_term_rent/`**.
Это источник версии для разработки, CI и сервера. Каталог включается в архив
релиза; сервер читает его через `RENTAL_REFERENCE_DIR`. Локальный запуск подключает
его автоматически. В Angular assets справочники не копируются. Отдельный
искусственный пример остаётся в `backend/src/test/resources/reference-example/`.

Это разные виды данных:

1. **Исходная схема площадки** — поля, типы, варианты, ограничения, `when`.
2. **Common** — общие поля Автопоста. Одинаковые факты не дублируются по площадкам.
3. **Mapping / план подготовки** — связи common → нативное поле, точные коды,
   разрешённые преобразования, зависимости подготовки, константы и ограничения.
4. **Binding** — селекторы, действия, порядок заполнения и проверка результата
   в браузере. Не содержит бизнес-преобразований.
5. **Card** — названия подключённых площадок, общие варианты, подписи,
   группировка редактора, единая адресная проекция.

Исследовательский mapping этапа B и исполняемый план сейчас различаются:
`integration/mapping_*.json` сохраняет результат исследования;
**активный runtime-источник — `runtime/preparation_*.json`**, указанный в manifest.
Он содержит только проверенные преобразования поддерживаемого исполнителя.
Изменение исследовательского mapping само по себе не активирует новые правила.
Переход к новому плану — отдельное проверяемое обновление комплекта с хешами
исходной схемы и common. Не следует одновременно редактировать оба файла как
независимые рабочие настройки.

В новом комплекте `manifest.json` явно задаёт `format_version: 1`,
`source_schema_version: "2.1"`, `category_id`, пути `common`, `card` и реестр
`platforms`. Каждая площадка содержит пути `schema`, `plan`, `binding`.
Полный пример находится в тестовом комплекте; пути относительные, выход за его
каталог запрещён. Размер каждого JSON ограничен 5 МиБ.

Действующий комплект 1.2 пока поддерживается отдельным режимом
совместимости: без manifest используются прежние пути, реестр из `runtime/card.json`
и вложенные факты `fill_rule`. Старые browser bindings не становятся автоматически
bindings версии 2.1 и не исполняются этим модулем.

В 2.1 исходные факты находятся непосредственно в Option; `choice.value` сохраняет
тип кода, enum требует `options_complete`. Адаптер строит прежнее внутреннее
представление для исполнителя и редактора, не переписывая исходный файл.
Для этого редактора комплект должен содержать одну конечную категорию:
подкатегории нельзя молча склеивать или наследовать. Общий файл и схемы площадок
не заменяются догадками ИИ при запуске сервера.

Проверяются контрольные суммы, версии, уникальность ID, ссылки на common и
нативные поля, известные виды преобразований, условия, циклы зависимостей,
полнота списка записей binding и минимальный контракт `ready`. Это проверка
структуры, **не подтверждение работоспособности внешней формы**. Принятие файлов,
адресные справочники, неизвестные ограничения и неподдержанные действия требуют
проверки конкретного адаптера. `publicationReady` остаётся false.

## Адрес из описания

После проверки адреса типовые префиксы города, улицы и дома убираются из отдельных
полей. Исходная адресная строка сохраняется; тип города/улицы сохраняется отдельно
для сопоставления одноимённых подсказок. В браузер передаются чистое значение
для ввода и `matchValue` для проверки типа, когда исходные сведения ещё соответствуют
текущему имени (ручная правка имени не должна использовать прежний тип).

Распознавание различает общее число комнат и раздельные комнаты. Одно точное
число используется для обоих полей; studio/5+ не превращаются в точное число.
Явные пары «этаж 3 из 9» и «3/9 этаж» не смешиваются. Неуточнённые рубли — BYN,
явно российские — RUB. ИИ составляет отдельные заголовок до 100 символов и
краткое описание до 500 символов по преимуществам из исходного текста; полное
описание остаётся исходным. Сервер проверяет границы длины и цитаты-основания.

`RentalAiPolicy` принимает только адресную цитату из описания. `LiteralAddress`
выделяет её части и проверяет буквальное происхождение частей, предложенных ИИ.
Идентификаторы, координаты и признак подтверждения от ИИ не принимаются.
`RentalAiAddressResolver` вызывает существующий `AddressService` в контексте
кабинета: поиск, сопоставление города/типа улицы/дома/корпуса и подтверждение
единственного совпадения. В DaData передаётся адресная цитата, не всё описание.
При отсутствии совпадения, неоднозначности или сбое сохраняются распознанные
части с `provider: manual` и причиной в `resolution`; Angular открывает ручные
поля. Остальные предложения ИИ продолжают работать. Старую карточку с одной
строкой адреса можно дополнить повторным заполнением с ИИ; ручные изменения
сначала предлагаются к подтверждению. Расширение получает ту же структуру
`address`, что и после ручного выбора подсказки. Для последовательных запросов
ИИ и DaData таймаут прокси составляет 90 секунд.

## Angular

Файлы находятся в `frontend/src/app/rental/`:

- `rental-models.ts` — типы DTO; `rental-api.ts` — единственная функция транспорта.
- `RentalDraftStore` — отдельный экземпляр на редактор: автосохранение, очередь
  записей, ревизии, открытие/удаление, загрузка схемы и подготовка.
- `RentalAiAssistant` — запрос предложений, защита от позднего ответа, принятие
  отдельных замен. Использует состояние карточки; не обращается к DOM.
- `RentalViewModel` — применимость полей, подписи, фильтрация и объединённые ошибки;
  не сохраняет и не делает сетевых запросов.
- `RentalDraftEditor` — изменение значений, адресно-зависимых фактов, площадок
  и устаревших полей. Не обращается к DOM и не делает сетевых запросов.
- `RentalEditorComponent` — координация пользовательских событий, навигация
  и фокус. Его короткие делегаты сохраняют прежний контракт шаблона.
- `RentalFieldsComponent`, `AddressInputComponent`, `RentalSavedListComponent`,
  `RentalAiReviewComponent` — отдельные элементы интерфейса. Поиск адресов имеет
  собственный жизненный цикл; отображение списка и предложений ИИ не владеет API.

Состояние не является глобальным singleton: смена кабинета или уничтожение
редактора не переносит карточку в другую сессию. Прежний API остаётся совместимым.

## Подключение и обновление площадки

Для адресных подсказок `runtime/browser_*.json` задаёт `autocomplete`: область
поиска `scopeSelector`, элементы `optionSelector`, текст `labelSelector`, признак
загрузки `busySelector`, вид адреса `kind` и подтверждение `value-and-closed`.
`contextParts` (`region`, `district`) и `contextSelector` позволяют различить
одноимённые населённые пункты. Сервер подставляет в `matchContext` только компоненты
адреса текущей карточки. Нативные коды других адресных сервисов не используются.
Отдельный `extension/rental-autocomplete.js` обрабатывает эти декларативные правила:
сохраняет фокус, сопоставляет название и тип, ждёт стабильный единственный вариант,
затем проверяет выбранный текст и закрытие списка. Зависимость `after` разрешает
следующее поле только после подтверждения предыдущего. Разметка Realt проверена
03.11.2026, автоматический обработчик — на воспроизведённой DOM-структуре.

1. Этап A по актуальным `parsing_rule.txt` и `parsing_format_rule.txt`: получить
   исходную схему и binding с доказательствами. Не менять `parsing_input.txt`.
2. Отдельный этап B: сопоставить семантику полей/вариантов с существующим common.
   Добавлять новый общий факт лишь если соответствующего ещё нет.
3. Собрать план подготовки из поддерживаемых обработчиков, явно сохранить
   неизвестные ветви для проверки. Добавить площадку в manifest и card.
4. Обновить комплект в Git и включить изменения в PR. Сырые доказательства, HAR
   и сессии сохранять отдельно. Хеши плана — SHA-256
   UTF-8 компактной JSON-сериализации исходной схемы/common, с исходным порядком
   свойств, как у Jackson. Не хешировать отформатированные байты файла.
5. Проверить комплект без запуска сервера:

   ```sh
   java -jar backend/target/autopost-api.jar --validate-rental-reference=data/rental/apartments_long_term_rent
   ```

6. Выполнить контрактные тесты, подготовку вымышленной карточки и проверку
   разрешённых ветвей внешней формы. Подключение нового вида browser-действия
   требует кода адаптера и проверки, одного JSON недостаточно.
7. Собрать релиз: упаковка проверяет и включает комплект из Git. Развёртывание
   устанавливает `RENTAL_REFERENCE_DIR=/opt/autopost/current/data/rental/apartments_long_term_rent`
   и переключает приложение со справочниками вместе. Сохранять предыдущий релиз,
   конфигурацию и базу для отката. Не редактировать файлы по одному на сервере;
   кэш проверяет mtime/размер, а не перечитывает всё на запрос.

Новая площадка с уже поддержанными типами и преобразованиями подключается
данными. Пятая искусственная площадка и новый комплект 2.1 проверяются тестами.
Сайт не предоставляет отдельный API справочников; рабочие JSON доступны команде
в репозитории вместе с исходным кодом.

При проверке действующего набора обнаружено одно неоднозначное название жилого
комплекса Kufar с двумя кодами. Из активного плана удалены оба автоматических
соответствия; исходные схемы и исследовательский mapping сохранены. Название в
карточке остаётся, подготовка сообщает о неподтверждённом соответствии. Комплект
перенесён из снимка `2026-11-02-modular-card` в Git и содержит manifest с форматом 1.2;
переход всех исходных схем и browser bindings на 2.1 не объявляется завершённым.

## Контроль регрессий

`npm test` включает проверки границ фронтенда и циклов импортов по AST TypeScript.
Компоненты не импортируют транспорт и хранилище, адаптеры не зависят от UI и
состояния редактора. Backend `ArchitectureTest` использует ArchUnit для проверки
зависимостей скомпилированных классов: HTTP-слой не обращается к репозиториям,
прикладной слой не зависит от HTTP/JDBC-реализаций, предметные правила не зависят
от Spring. Сохранена проверка исходников аренды на SQL вне persistence,
HTTP/Servlet в предметных модулях и вшитые ID четырёх площадок.
`ReferenceBundleTest` проверяет формат 2.1, типы кодов, хеши, кэш, изоляцию снимков,
неизвестные ссылки/обработчики, циклы, пути и неполные bindings.
Тест также загружает реальный комплект из репозитория и проверяет его согласованность.
Прежние тесты карточек, ИИ, адресов и конкурентного сохранения остаются.

Эти проверки запускаются существующим CI. Полный набор:
`npm test`, `npm run test:frontend`, `npm run build`.
