ЕДИНАЯ КАРТОЧКА АРЕНДЫ · КОНТРАКТ 2
2026-11-02

Цель: один редактируемый факт — одно место хранения и ввода. Поля карточки
покрывают объединение подтверждённых смыслов, включая уникальные поля площадки.
Неизвестное значение, false, ноль и отсутствие значения различаются.

Слои и совместимость

Исходные схемы форм хранятся в data/rental/apartments_long_term_rent в GitHub. Исследовательское правило
«common при наличии минимум двух площадок» сохраняется для результатов парсинга.
Для пользовательской карточки применяется отдельный контракт 2: runtime/card.json
явно задаёт version=2. На развёртывании используется отдельный снимок reference:
копия common расширена уникальными фактами и перегруппирована для редактора.
Существующие канонические ID сохраняются; ссылки и хеши preparation-планов
пересчитываются. Снимок исследовательского common версии 1 остаётся доступен
для сравнения. Не смешивать новые планы со старым common.

runtime/card.json содержит:
- version: 2;
- platforms: объект id -> {name}; источник реестра, без фиксированного лимита 4;
- canonicalValues: конечные канонические варианты; числа с открытым диапазоном
  не следует ограничивать списком одного из поставщиков;
- valueLabels: пользовательские подписи канонических значений;
- addressProjection: общий legacy id -> часть объекта address;
- expandedGroups: первоначально раскрытые смысловые группы;
- addressDependentFacts: факты, сбрасываемые при смене адреса.

common хранит смысловые группы и поля ровно по одному разу. Техническая группа
address_projection исключается из редактора. Она нужна только для совместимости
обработчиков. EditorCardDecorator.decorate добавляет uses для выбранных площадок;
исходные коды в форме пользователю не показываются.

preparation_<id>.json содержит проверенные преобразования, константы, проверки,
address_bound_fields (все устаревающие native address/coordinate значения) и
явные deferred_fields с причинами неподдержанной автоматизации. Новое поле
подключается данными; новый механизм интеграции может потребовать нового адаптера.
Справочник не содержит исполняемый код, eval или удалённые скрипты.

Состояние карточки

modelVersion: 2; schemaVersion: хеш common, card и всех preparation-планов;
values: канонические факты; address: единый объект; platforms: выбранные площадки.
extras не являются вторым пользовательским источником истины.
legacy содержит неразрешённые расхождения старых данных; resolvedLegacy — их
сохранённую историю после осознанного решения пользователя.

Однозначные обратные маппинги переносят extras в
values; неоднозначные, неподдержанные и противоречащие значения остаются в legacy.
Нельзя угадывать, какой из нескольких источников породил один общий checkbox.
Адресные extras никогда не подаются как подтверждённый адрес новой карточки.
Старые записи, файлы и конфликты не удаляются молча.

POST normalize обновляет правила текущей формы в памяти страницы. Подготовка отклоняет устаревший schemaVersion.

Адрес

Поиск и ручной ввод меняют один address. Текст незавершённого поиска сохраняется.
В ручном режиме доступны населённый пункт, улица, дом с буквой, корпус, область,
район. Редактирование снимает подтверждение координат и сбрасывает зависимые
сведения. Поздний ответ поиска не применяется после смены карточки или блокировки
редактора. ID DaData/OSM не выдаются за ID площадки.

Native address resolvers пока не завершены. Подготовка сообщает об этом в одном
общем сообщении с перечнем площадок, не предлагает вводить адрес четыре раза и
не объявляет такой результат готовым к публикации. Это остаётся пробелом
интеграции, а не решённой автоматизацией. Для закрытия нужны подтверждённые
объекты адресов/зависимости и проверка в авторизованной форме каждой площадки.

Подключение следующей площадки

1. Получить разрешённую схему формы и доказательства её условий, типов и кодов.
2. Сопоставить каждое конечное поле со смыслом карточки; при новом смысле добавить
   один canonical id в подходящую группу. Не сливать поле лишь по похожей подписи.
3. Записать типизированные mappings и константы, сохраняющие точность и смысл.
4. Зафиксировать неподдержанные области явно; пустой справочник не считать полным.
5. Обновить контрольные суммы и реестр runtime/card.json.
6. Проверить каждый source leaf, все enum/multi варианты и условные ветви;
   обновить приватную матрицу покрытия. Покрытие поля не равно полноте всех значений.
7. Прогнать подготовку, изменение адреса, нормализацию старых
   карточек, конфликт ревизии, изоляцию кабинетов и отображение без отдельной формы.

RentalCardTest создаёт пять синтетических площадок в TempDir и проверяет,
что все пять проходят через единый редактор и подготовку без изменения приложения.
Синтетические тесты публичны; реальные схемы, варианты и подробная матрица — нет.

Ограничения

Это редактор и проверка подготовки. Здесь нет автоматической публикации квартиры,
полного разрешения native адресов, принятия фотографий площадкой или автоматического
включения платных возможностей. Такие ограничения отображаются явно. Ключи API
остаются на сервере/в Worker; клиент не получает секреты. Изоляция кабинетов
и проверка ревизии при сохранении продолжают действовать; normalize требует
авторизации в текущем кабинете.
