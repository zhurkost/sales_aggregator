ДЕРЕВЬЯ ЗАВИСИМЫХ ВАРИАНТОВ
Нормативное дополнение parsing_format_rule.txt 2.2 | 2026-11-11

1. ОБЛАСТЬ ПРИМЕНЕНИЯ

childOptions описывает прямую иерархию выбора с одним родителем у каждого узла.
Перечень таких цепочек определяется заданием. Другие перечисления сохраняются
плоскими массивами options; зависимость их поля или варианта записывается в when.
Не превращать каждую обнаруженную зависимость формы в дополнительное дерево.
Правило одинаково для любых категорий и произвольного числа уровней. Названия
уровней не зашиваются в алгоритм. Пример ниже: класс → подкласс → исполнение.
Это не дерево категорий Category.categories и не группировка формы group.options.
Обычные независимые списки остаются плоскими. Зависимости от нескольких факторов,
условия появления полей и ограничения по-прежнему описываются when.

Год и дата не добавляются в цепочку и не служат критерием сопоставления/фильтрации
её узлов: все наблюдаемые варианты разных лет собираются под одним родителем.
Не удаляй реальные ограничения источника: если площадка фильтрует по дополнительному
полю, запиши это в when/отчёте и проверь при переносе. Если без года нельзя различить
два одноимённых варианта, соответствие остаётся needs_review, а не угадывается.

2. СХЕМА ПОЛЕЙ И УЗЛОВ

Все поля уровней явно объявляются как Option типа enum в category.options либо
group.options. У поля первого уровня options содержит корневые choice. У поля
следующего уровня parent_option_id указывает на enum-поле предыдущего уровня,
options: []: его варианты хранятся под родительскими choice, а не дублируются.
Это единственное дополнительное основание для пустых options известного enum;
описание полей уровней сохраняется ради required/validation/when и binding.
В текущем расширении контракта одно дерево — одна цепочка полей, без пропуска
уровней и без нескольких разных дочерних полей у одного уровня. Для ветвящегося
набора полей использовать отдельные деревья/when или needs_review.

Каждый choice дерева содержит:
  id              — обычный стабильный Option.id;
  name            — видимая подпись, в common — согласованная общая подпись;
  description     — назначение/уточнение, без значений пользовательского объявления;
  type            — "choice";
  options         — [];
  level           — точный id enum-поля, вариантом которого является узел;
  childOptions    — массив choice следующего уровня, [] в конце ветви;
  options_complete — подтверждена ли полнота непосредственного childOptions;
  value           — для исходника площадки точный скалярный код или null;
                    для choice общего дерева не нужен: выбор хранится по id;
  when            — только дополнительные наблюдаемые ограничения, если нужны.

level — ссылка, не произвольный номер или подпись уровня. У корневого choice
level равен id поля, в options которого он находится. Для каждого дочернего
choice поле по его level обязано иметь parent_option_id, равный level родителя.

ID уникальны среди полей и вариантов всей категории, включая обе вложенности
options и childOptions. Одинаковый нативный value может встречаться у разных
родителей: это разные узлы с разными id и отдельным контекстом. Не используй
индекс списка как ID. Сохраняй ID при смене подписи, порядка или повторном сборе;
перенос узла в другую ветвь требует проверки смысла и всех связей, не тихой подмены.
Циклы, несколько родителей и повторное хранение узла запрещены. Индекс родителей
строится в памяти по вложенности; parentId у choice хранить не требуется.

options_complete у корневого enum описывает полноту корневого списка.
У зависимого enum он означает полноту вариантов этого уровня по всем родителям
в заданном объёме; true нельзя ставить, пока не закрыты родительские ветви.
У choice он описывает только непосредственных детей. Полное поддерево требует
полноты на каждом уровне. Для подтверждённого конца ветви: childOptions: [],
options_complete: true. Для недоисследованной ветви: [], false и причина в отчёте.
Знать подписи всех вариантов не означает знать их коды: null остаётся неизвестным.
Полнота common относится к переданному набору источников, а не ко всем площадкам.

3. СБОР И ОБЪЕДИНЕНИЕ

На A выбирай родителя, дождись обновления списка, сохрани детей с их контекстом,
затем исследуй следующий уровень. При смене родителя старый список не считается
ответом для нового. Учитывай пагинацию, задержки, скрытые и недоступные ветви.
Объединяй наблюдения одной ветви без дублей; разные коды/смыслы с одинаковой
подписью не склеивай. Не обходи ограничения доступа. Все пробелы перечисли в отчёте.

На B рекурсивно обходи и options, и childOptions. Сначала сопоставляй поля уровней,
затем узлы сверху вниз. Имена, регистр, пробелы, подтверждённые синонимы и смысл
помогают найти кандидатов; соответствие подтверждай в контексте всей цепочки
уже сопоставленных родителей. Глобальное совпадение name недостаточно.
Не добавляй отдельную систему идентификаторов: используются те же Option.id,
common_option_id и platform_option_id, что в остальных схемах.

Поле включается в common при подтверждении смысла минимум двумя площадками.
Отдельный вариант может поддерживаться одной; это явно отражается покрытием.
Общие поля дерева сохраняют enum/choice и childOptions, в отличие от плоских
исследовательских полей text. Существующие плоские справочники и недвижимость
автоматически не мигрируются. Уникальные поля исходников не теряются.

4. ПРЯМОЙ МАППИНГ

Корень mapping остаётся {category_id, platform, fields}, для деревьев добавляется
nodes. В fields для каждого сопоставленного поля уровня:
  {common_option_id, platform_option_id,
   conversion: {kind: "node_lookup", on_unmapped: "needs_review"}}.
В nodes для каждой подтверждённой пары вариантов:
  {common_option_id, platform_option_id}.
У fields обе ссылки ведут на поля; у nodes обе — на choice. ID целевого узла не
является кодом сайта: для установки берётся его value после проверки when.
Неизвестный value не выдумывается; выбор по name возможен только по отдельно
подтверждённому binding match:text. Это не новый поиск соответствия между сайтами.

Прямые связи создаются на КАЖДОМ подтверждённом уровне, а не только у листьев.
В пределах одной площадки один общий узел имеет не более одной целевой записи.
Соответствие дочерних узлов допустимо только при прямом соответствии родителей
и полей level. Коллизии, разные глубины или несогласованные родители — кандидаты
в отчёте, а не готовые nodes. Схлопывать уровни и обходить пропущенное звено нельзя.
Одинаковый узел не должен неоднозначно принимать разные общие смыслы; объединять
подтверждённые синонимы следует на этапе построения common.

finalId не вводится. Не предусмотрены запасной поиск по конечному узлу, совпадение
по последнему имени или автоматический выбор первого варианта. Из целевого листа
нельзя достраивать отсутствующие прямые связи маппинга. Если площадка не имеет
более глубокого уровня, заполняется только явно сопоставленный префикс; отсутствие
переноса остальных уровней отмечается, не объявляется полным соответствием.

5. ВЫБОР ПОЛЬЗОВАТЕЛЯ И ПЕРЕНОС

Логический контракт карточки: values[<id корневого поля>] = <id выбранного choice>.
Можно выбрать любой узел, не только лист. Значения остальных уровней получаются
из единственного пути к нему; хранить противоречащие друг другу независимые
выборы уровней нельзя. Если выбран промежуточный узел, потомки неизвестны.
Эта форма карточки — требование будущей интеграции, не описание нынешнего runtime.

Для подготовки: проверить принадлежность узла корню, восстановить общую цепочку,
для каждого известного уровня применить прямые fields/nodes, проверить целевую
цепочку, ограничения и коды. При пробеле остановить зависимую часть; уже известный
согласованный префикс можно подготовить с явным needs_review по остатку.
Это относится к корректному частичному mapping. Структурно противоречивый mapping
(например, связь потомка без прямой связи родителя) отклоняется при проверке файла.
Если площадка требует неизвестный уровень, запросить уточнение, не выбирать
единственного ребёнка автоматически: единственный доступный вариант не является
фактом пользовательского объявления.

Бэк владеет индексом, прямыми соответствиями, проверкой цепочки и доступными
вариантами. Фронт показывает полученные варианты и состояние загрузки/неизвестности;
при смене родителя несовместимый дочерний выбор сбрасывается. Устаревший ответ на
предыдущий выбор не подменяет новый список. Это требования интеграции, а не готовый API.
ИИ распознаёт выбор по общему дереву с точной цитатой, а не нативному коду сайта.
Неоднозначный потомок остаётся неизвестным; узнавание родителя не даёт права
придумать ребёнка. Наличие варианта в справочнике не является фактом объявления.

Binding описывает каждое поле уровня по его option_id, а не каждый choice.
depends_on содержит ID родительских полей. После выбора родителя расширение
ждёт актуальную ветвь, заново находит элементы, выбирает подготовленный вариант
и проверяет фактическое значение. Ручные правки сохраняются. Публикация,
подтверждения и продвижение остаются пользователю.

6. ПРИМЕРЫ И ПРИЁМКА

docs/parsing/examples/child-options/ содержит учебные, не реальные данные:
  common.json, platform.json — три уровня с обычными Option.id;
  mapping.json — прямые связи полей и всех узлов;
  binding.json — needs_review, так как учебные селекторы не наблюдались.
Одна условная площадка демонстрирует синтаксис; это не результат этапа B
и не доказательство выполнения требования двух независимых источников.

Проверки сдачи (с результатом и доказательством для каждого пункта):
1. JSON, версия 2.2, уникальные ID во всём дереве, ссылки level/parent_option_id,
   отсутствие циклов/нескольких родителей, отсутствие finalId.
2. Дочерние уровни и полнота каждой ветви; пустое true отличается от пустого false.
3. Прямые связи каждого подтверждённого уровня; совпадение имён в чужой ветви
   не создаёт соответствия. Несопоставленные узлы перечислены с причинами.
4. Выбор корня, промежуточного узла и листа восстанавливает ровно известный путь.
5. Смена родителя убирает несовместимого ребёнка; поздний ответ не возвращает его.
6. Отсутствующая связь, неизвестный код, обязательный неизвестный потомок,
   разные глубины и несовместимые родители не превращаются в успешный перенос.
7. Годы не используются для построения/сопоставления дерева; реальные дополнительные
   ограничения формы сохраняются и не подменяются утверждением о полной доступности.
8. Прежние плоские lookup/files и активные схемы недвижимости не изменены этой
   спецификацией. ID и value не перепутаны, типы кодов сохранены.
9. Отдельно указано, что проверено по файлам, что валидатором версии 2.2, что в UI,
   а что требует реализации. Статический пример не доказывает работу интерфейса.

7. СОВМЕСТИМОСТЬ

Документ определяет новый исследовательский контракт 2.2. Текущая реализация
SchemaCompatibility принимает 1.2/2.1; node_lookup, nodes и childOptions не
подключены к production-редактору, ИИ и расширению. Существующие данные, исходные
задания parsing_input.txt и исторические отчёты не переписываются задним числом.
До отдельной задачи интеграции нельзя менять source_schema_version активного
manifest, отключать проверки версии или объявлять 2.2 совместимым с runtime.
