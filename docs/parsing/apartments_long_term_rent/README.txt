Версия задания: 1.0 | Дата: 2026-11-01

Цель: получить проверенные описания форм Kufar, Onliner, Realt и Domovita,
одну общую категорию и явные соответствия для подготовки объявления.
Это задания на исследование справочников, а не на сбор объявлений или цен.

Базовая ветка: migration/angular-spring.
Проверенная база: bc3297d324ba561738bc3aece4197c3e65fda151.
Контракты в корне репозитория: parsing_rule.txt v1.3 и
parsing_format_rule.txt v1.2. Стек приложения: Angular + Spring.
Если контракты изменились, сначала перечитать их и отразить новую версию в отчёте.

ЕДИНАЯ КАТЕГОРИЯ

category = apartments_long_term_rent
name = Долгосрочная аренда квартир
Рынок: Беларусь. Действие: сдать квартиру целиком на длительный срок.
Не входят: посуточная аренда, комнаты, койко-места, дома, коммерческие помещения,
продажа, объявления «сниму». Студия входит, если площадка считает её квартирой.
Не придумывать универсальный порог длительности аренды в месяцах.

ПОРЯДОК РАБОТЫ И ВЛАДЕНИЕ ФАЙЛАМИ

1. Четыре независимых агента исследуют по одной площадке. Каждый читает оба
   корневых контракта, worker_rules.txt и свой parsing_input.txt ниже.
   Каждый пишет только свои исходную схему, привязки и отчёт.
2. После получения минимум двух проверенных схем запускается интегратор.
   Только он создаёт common и ВСЕ mapping-файлы. После третьей и четвёртой
   площадки он повторяет сверку со всеми источниками и обновляет соответствия.
   Если нужны законченные результаты сразу по четырём, запускать его после
   завершения четырёх исследований, включая отчёты о недоступных ветвях.
3. Работники не редактируют общий файл одновременно. Это разделение этапов
   раздела 3 parsing_rule.txt между ролями; правило двух источников сохраняется.
4. Для отдельных checkout использовать одну базовую ревизию и передать результаты
   интегратору вместе с отчётами. В общем checkout владение файлами такое же.
   Чужие изменения не откатывать; исходные контракты и код приложения не менять.
5. При общем браузере у каждого исследователя своя вкладка площадки. Не менять
   страницу/аккаунт в чужой вкладке. Если доступный инструмент управляет только
   одной общей вкладкой, исследования выполнять по очереди, сохраняя прогресс.

ГРАНИЦЫ ГОТОВНОСТИ

Завершение задания — проверенные файлы и отчёты. Подключение к Spring,
отрисовка Angular и исполнение привязок расширением — последующий этап.
Нельзя сообщать, что публикация работает, только потому, что JSON валиден.

В текущем формате однозначно заданы identity, lookup и files. Формат обработчика
общей текстовой цены/площади -> числового поля площадки пока не определён.
Такие преобразования интегратор описывает отдельно как кандидаты; выдавать их
за identity запрещено. Новых исполняемых conversion.kind эти задания не вводят.
Это известный пробел интеграции, а не причина выдумывать значения или не собирать
сами числовые поля. Поля, доступные только одной площадке, тоже сохраняются.
