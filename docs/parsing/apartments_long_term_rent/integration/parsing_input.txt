ЗАДАНИЕ ИНТЕГРАТОРУ: ОБЩАЯ КАТЕГОРИЯ И МАППИНГИ
Версия: 1.0 | Дата: 2026-11-01

Прочитай parsing_rule.txt, parsing_format_rule.txt в корне репозитория,
README.txt, worker_rules.txt и все четыре задания этого набора.
category = apartments_long_term_rent
platforms = kufar, onliner, realt, domovita
Название общей категории: Долгосрочная аренда квартир.

ВХОД
Исходные схемы, привязки и отчёты в data/parsing/apartments_long_term_rent/.
Убедись, что они относятся к одной категории и согласованным версиям контрактов.
Не считай наличие файла подтверждением его полноты: прочитай отчёты и источники.
Не собирай новые данные с сайтов вместо отсутствующих доказательств незаметно.
Для существенного пробела сформулируй адресное задание соответствующему агенту.

ВЛАДЕНИЕ ВЫХОДОМ
Только ты редактируешь в том же каталоге:
  apartments_long_term_rent_common.json
  mapping_apartments_long_term_rent_kufar.json
  mapping_apartments_long_term_rent_onliner.json
  mapping_apartments_long_term_rent_realt.json
  mapping_apartments_long_term_rent_domovita.json
  report_apartments_long_term_rent_common.txt
Исходные файлы площадок не переписывай. Их исправления возвращай владельцам.
Нет проверенной схемы площадки — нет рабочего mapping для неё; причина в отчёте.
Меньше двух проверенных площадок — только отчёт, без преждевременного common.
При двух источниках и отсутствии совпадений common содержит категорию с options:[],
а маппинги доступных площадок имеют fields:[], с объяснением в отчёте.

ОБЪЕДИНЕНИЕ
1. Проверь каждую исходную схему по контракту. Составь таблицу доказательств:
   смысл -> Option.id площадок -> URL/секция/дата -> единицы/варианты/зависимости.
2. В common включай только поля с подтверждённым одинаковым смыслом минимум
   на двух разных площадках. Поддержка всеми четырьмя не требуется.
   Уникальные поля не теряй: они остаются в исходных схемах, а дополнительные
   обязательные вопросы по конкретной площадке перечисляются в отчёте.
3. Общий root.id = apartments_long_term_rent. Все Category/Option имеют полный
   набор обязательных свойств. Общие листья text или files, группы group.
   Не копируй enum/number/boolean из исходной формы в общий файл.
4. Сохраняй существующие общие ID; для новых используй понятные стабильные
   смысловые имена с rental. или location. и т. п. Не включай имя площадки
   в общий ID и не объявляй предлагаемую конвенцию доказательством совпадения.
5. Для каждого общего text-поля в description и отчёте опиши представление:
   единицы, формат дробей/даты, допустимые канонические строки или разделители.
   Не назначай value_from, пока не проверен реальный контракт входного объявления;
   произвольные listing.* и attributes.* не считать уже согласованным API Spring.
6. Required и ограничения одной площадки не переносить на все. На уровне общей
   формы пользователь может оставить значение неизвестным; проверка готовности
   каждой площадки опирается на её исходную схему. Не заменять null на false/0.

ОСОБЫЕ СЕМАНТИЧЕСКИЕ ПРОВЕРКИ
  - плата за месяц, плата за сутки, коммунальные, депозит/залог, комиссия;
  - денежный залог и число месячных платежей; сумма и валюта вместе;
  - площадь общая, жилая, кухни; этаж квартиры и этажность дома;
  - студия, число комнат и отдельная комната в сдаваемой квартире;
  - регион/населённый пункт/район/микрорайон/метро/улица/дом/координаты;
  - мебель, техника, состояние и свободное описание;
  - допускаются животные/дети, запрещены, не указано;
  - дата доступности и минимальный срок договора;
  - автор, собственник, представитель, агентство и контакты профиля;
  - фотографии объекта, планировка, видеоролик/ссылка и документы.
Совпадение подписи не доказывает совпадение смысла. Не добавляй поля из списка,
если два источника их не подтвердили. Не выводи common из предположений ИИ.

МАППИНГИ
Направление только common -> платформа. category_id = apartments_long_term_rent.
Ссылки должны разрешаться в передаваемых схемах, enum-коды — точь-в-точь
соответствовать choice.value с сохранением исходного JSON-типа.

identity допустим только при совпадении представления И типа. Общая строка
"1200.50" -> number не identity. Lookup хранит полные подтверждённые from/to
и on_unmapped:needs_review. Для true/false общего text заранее зафиксируй
канонические строки, неизвестность не преобразовывай в ложь.

Для чисел/дат/списков/единиц/составных значений без согласованного обработчика
не добавляй рабочую запись: в отчёте укажи исходные и целевые ID, типы, форматы,
единицы, входные роли, допустимые значения и требуемую операцию. Новые kinds
этим заданием не определены. Площадка с такими пробелами не готова к автозаполнению
всех своих обязательных полей, даже если остальная часть mapping валидна.

Фиксированную ветвь «сдать квартиру надолго» сохраняй как подтверждённую
константу схемы площадки/маршрута; не создавай ради неё несуществующее общее поле.
Условия и зависит-от сохраняют ID и значения соответствующей схемы. Условия
над числом нельзя переносить на общий text без определённого преобразования.

Files остаются в fields: kind=files, preparation.operations:[] для подтверждённого
переноса без изменения, on_incompatible:needs_review. Не придумывай сжатие,
обрезку, конвертацию, выбор первых N, хостинг или скачивание внешнего видео.
Разные роли файлов не объединять. Требования назначения проверяются отдельно.

ПРОВЕРКА И ПЕРЕДАЧА
Проверь JSON, свойства, ID, ссылки, типы, enum-коды, when/depends_on и циклы;
все общие поля должны иметь минимум две площадки с доказательствами.
Проверь каждый mapping против обеих схем и привязки против схем своей площадки.
Полная форма включает уникальные поля площадок: common не является их заменой.
Добавление третьего/четвёртого источника требует проверки всех прежних маппингов.
Частичная новая проверка не означает исчезновения старого подтверждённого поля.

Итоговый report_apartments_long_term_rent_common.txt содержит:
  - дату с часовым поясом, версии контрактов и SHA-256 всех входных/выходных JSON;
  - перечень источников и их реальное покрытие;
  - таблицу каждого общего поля с подтверждениями минимум двух площадок;
  - канонические представления и основания сопоставлений;
  - уникальные поля по площадкам: обязательные, необязательные, неизвестные;
  - отсутствующие/неоднозначные маппинги и требуемые обработчики;
  - по площадкам: готовность схемы, маппинга, привязок, недоступные ветви;
  - изменения к прежним результатам и адресные задания для закрытия пробелов.

Отдельно опиши будущую передачу данных, не реализуя её в этом задании:
ИИ выбирает категорию из имеющегося каталога и предлагает значения известных
полей; пользователь подтверждает их; Angular отображает common и дополнения
выбранных площадок; Spring хранит и отдаёт схемы/версии; подготовка площадки
использует её mapping и проверяет required/when/validation перед заполнением.
Неизвестные факты ИИ оставляет пустыми. Данные справочников не вшиваются в код.

Не изменяй Angular/Spring, расширение, исходные контракты или действующие объявления.
Готовность JSON не означает, что исполнитель маппингов/привязок уже реализован
или что конечная публикация проверена. Итог — проверенные данные и ясные пробелы.
