# Подготовка полного переноса в Cloudflare

Статус на 2026-11-01: подготовка, **не production deployment**.
Основной сайт и его база продолжают работать на VPS. Диагностический Worker
`autopost-dadata-probe` подтвердил доступ к DaData из Cloudflare, включая вызов с VPS.

## Доступ и тариф

Wrangler авторизован для Workers и Containers. Проверка `wrangler containers list`
возвращает отказ: аккаунту требуется Workers Paid. В панели Cloudflare подтверждён
текущий тариф Free. Workers Paid стоит $5/месяц плюс использование; покупка тарифа
ещё не подтверждена и не выполнена.

Официальные условия: https://developers.cloudflare.com/containers/platform/pricing/

## Предлагаемая схема с сохранением Angular и Spring

1. Angular — Workers Static Assets, закрытые той же защитой входа, что и API.
2. Spring Boot / Java 17 — Cloudflare Containers; начать с одного экземпляра basic.
3. Пользовательская база — постоянное хранилище Cloudflare D1. Нужна адаптация
   слоя Database: текущий JDBC SQLite нельзя просто направить на D1.
   Требуется сохранить атомарность массовых изменений, контроль ревизий и
   изоляцию кабинетов. Подмена транзакций несколькими независимыми HTTP-запросами
   недопустима.
4. Закрытые справочники площадок — приватное хранилище, доступное только серверу;
   не Workers Static Assets и не публичный Git-репозиторий.
5. DaData, OpenRouter и служебные ключи — Cloudflare Secrets. Браузер ключей не получает.

Диск Containers временный. Запуск существующей SQLite в `/data` без постоянного
хранилища не является завершённым переносом: после остановки контейнера данные
будут потеряны. Dockerfile в этой папке сам по себе эту проблему не решает.

Документация: https://developers.cloudflare.com/containers/faq/

## Что подготовлено и проверено

- Dockerfile Java 17 с непривилегированным пользователем и портом 8080.
- `node scripts/prepare-cloudflare-container.mjs` готовит строго ограниченный
  контекст сборки в `work/cloudflare-container`: только JAR и Dockerfile.
  Неожиданные файлы в контексте приводят к отказу. Контекст подготовлен локально;
  сам контейнер ещё не собран и не запущен.
- Согласованная резервная копия production SQLite создана через SQLite backup API
  на VPS и скопирована в игнорируемую локальную папку `work/cloudflare-migration`.
  База прошла `integrity_check` и `foreign_key_check`.
- В копии 3 профиля, 15 объявлений, 47 версий, 16 уведомлений, 9 запусков,
  1 настройка кабинета и 1 карточка аренды.
- `scripts/prepare-cloudflare-database.py` формирует приватный импорт с параметрами
  и проверяет его восстановление в пустую SQLite, включая внешние ключи и
  сравнение каждой строки. Пароли остаются хешами. Сессии не переносятся:
  на новом домене требуется обычный вход в существующий профиль.
- Самое большое поле объявления — 429843 байта. Поэтому данные выгружаются
  как параметры, а не строковые SQL-литералы: лимит текста SQL D1 — 100 KB.
  Проверка подготовленного импорта (101 инструкция) прошла без потери строк.
  Импорт в облачную D1 ещё не выполнялся.

Пример локальной подготовки приватного импорта:

```sh
python scripts/prepare-cloudflare-database.py work/cloudflare-migration/source.sqlite work/cloudflare-migration/d1
```

Выходные `bound-import.json` и `validation.json` содержат приватные данные либо их
контрольные суммы и остаются в `work/`, исключённой из Git. Их нельзя включать
в публичную сборку, выводить в логи CI или публиковать как статические ресурсы.

## Критерии переключения

Перед переносом рабочего адреса нужно реализовать и проверить постоянное
хранилище, развернуть контейнер, импортировать свежую резервную копию,
проверить вход старых профилей, объявления, сохранение аренды, DaData,
изоляцию пользователей, конфликты ревизий и сохранность данных после
принудительного перезапуска контейнера. Далее обновить разрешённый домен
расширения и проверить связь сайта с ним. До этого VPS остаётся рабочим источником
данных. При окончательном переключении нельзя оставлять два независимо
редактируемых экземпляра одной базы.
