УНИВЕРСАЛЬНАЯ СТРУКТУРА JSON ДЛЯ ПАРСИНГА КАТЕГОРИЙ ОБЪЯВЛЕНИЙ
Документ: parsing_format_rule.txt
Версия документа: 1.1
Дата: 2026-11-01
Статус: проект спецификации; не описание уже реализованного исполнителя.

1. НАЗНАЧЕНИЕ

Создать единый формат, в который можно приводить категории объявлений,
их поля и варианты заполнения с разных площадок. Формат не должен быть
ограничен автомобилями, запчастями или одной конкретной площадкой.

Внешний тип — Category, а не Option. Корневое значение JSON — Category[].
Категории могут содержать подкатегории и поля. Поля описываются типом Option.

Фотографии, видео и документы входят в эту же модель как Option типа files.
Они участвуют в парсинге, логическом сопоставлении и маппинге наравне с другими
полями. В общем файле категории конечные поля имеют type: "text", кроме
вложений: они сохраняют type: "files". Структурные группы сохраняют type: "group".
Правила создания файлов площадок, общего файла и маппингов — в parsing_rule.txt.

Разделяем два слоя:
  1) Универсальные категории, поля, варианты и правила работы с данными.
  2) Привязки к конкретной странице: селекторы, действия браузера, события,
     ожидания и проверки принятия значения сайтом.

Изменение HTML площадки должно требовать обновления привязки, а не изменения
универсального описания категории. JavaScript-код в JSON не хранится.

2. ОБЩАЯ МОДЕЛЬ

interface Category {
  id: string;
  name: string;
  description: string;
  categories: Category[];
  options: Option[];
}

interface Option {
  id: string;
  name: string;
  description: string;
  type: OptionType;
  fill_rule: FillRule;
  options: Option[];
}

Category:
  id          — постоянный идентификатор категории.
  name        — название для человека.
  description — описание категории; пустая строка допустима.
  categories  — вложенные категории, всегда массив.
  options     — поля и группы полей данной категории, всегда массив.

Option:
  id          — постоянный идентификатор поля, группы или варианта.
  name        — название для человека, может меняться и переводиться.
  description — назначение поля или пояснение варианта.
  type        — семантический тип поля, а не HTML-тег.
  fill_rule   — правила получения, преобразования и проверки данных.
  options     — дочерние поля либо варианты выбора, всегда массив.

Идентификаторы категорий уникальны внутри каталога. Идентификаторы Option
уникальны внутри всего дерева options одной категории. Ссылки option_id
и depends_on разрешаются внутри этой категории, включая вложенные группы.
Если на разных площадках используется общий идентификатор, он должен
обозначать одно и то же понятие, а не только одинаковое название.

Категории помещаются только в categories, а не в options.
Значения type = "category" у Option нет.
У Category нет fill_rule: это описание категории, а не поля формы.
Автоматическое наследование полей от родительской категории не подразумевается.
Если оно понадобится, правила объединения и переопределения описываются отдельно.

3. ТИПЫ OPTION

group      — группа полей: характеристики, контакты, доставка и т. п.
text       — текст, в том числе описание, телефон, VIN, артикул и OEM.
integer    — целое число.
number     — число, допускающее дробную часть.
boolean    — логическое значение true / false.
date       — календарная дата в формате YYYY-MM-DD.
datetime   — дата и время в ISO 8601 с явно указанным часовым поясом.
enum       — один вариант из списка options.
multi_enum — несколько вариантов из списка options.
choice     — конкретный вариант внутри enum или multi_enum.
files      — упорядоченная коллекция ссылок на фотографии, видео или документы.

group.options содержит поля и другие группы.
enum.options и multi_enum.options содержат варианты типа choice.
choice.options — пустой массив в версии 1.0.
У остальных конечных полей options — пустой массив.
Условные дополнительные поля описываются отдельными Option с fill_rule.when.

files.options — пустой массив: реальные вложения являются значением поля,
а не дочерними Option. Даже одиночное вложение передаётся коллекцией из одного
элемента; ограничение max_items: 1 задаётся при наличии такого требования.
Список типов выше применяется к исходным описаниям площадок. В общем файле
обычные конечные поля становятся text, а files не преобразуется в строку.

Не следует определять тип number только потому, что строка состоит из цифр:
артикул "000123" должен оставаться строкой с ведущими нулями.
Неизвестный по исходной странице тип требует уточнения; его нельзя выдавать
за подтверждённый тип или использовать для необратимого преобразования данных.

4. FILL_RULE — УНИВЕРСАЛЬНЫЕ ПРАВИЛА ДАННЫХ

Все свойства необязательны и используются по смыслу конкретного типа.
Пустой объект {} допустим, например для группы полей.

value_from:
  Путь к исходному значению в данных объявления.
  Примеры: "listing.price", "listing.title", "attributes.memory", "attachments.images".
  Это обращение к данным, а не выражение для исполнения.
  В версии 1.0 точка разделяет ключи объекта. Индексы массивов, вычисляемые
  выражения и буквальные точки внутри ключей не поддерживаются.
  Для files путь разрешается в массив AttachmentReference, а не в текст,
  строку JSON, base64 или список URL, разделённых запятыми.

value:
  Постоянное значение, прежде всего код варианта choice.
  Примеры: "BYN", "used", true, 0.
  Код отделён от name: "used" может отображаться как "Б/у".
  Не задавать value и value_from одновременно.

required:
  Обязательность значения: true или false. При отсутствии — false.
  Проверяется только для применимого по when поля.
  В результате неполного парсинга null явно означает "не установлено";
  это не false и не подтверждение готовности формы. Неизвестность отражается
  в отчёте и требует уточнения перед проверкой обязательности.

default_value:
  Значение при отсутствии данных. Используется только если явно задано.
  Не должно подменять неизвестные цену, пробег, состояние и другие факты.
  Для files запрещены value и default_value: реальные вложения выбираются
  для конкретного объявления и получаются только через value_from.

transform:
  Упорядоченный список разрешённых преобразований.
  Предлагаемый набор:
    trim         — убрать пробелы по краям строки;
    decimal_dot  — заменить десятичную запятую точкой;
    to_number    — преобразовать корректную числовую строку в число;
    to_integer   — преобразовать целое число без округления и обрезания;
    uppercase    — привести строку к верхнему регистру;
    lowercase    — привести строку к нижнему регистру.
  Неизвестные операции и неуспешные преобразования дают ошибку.
  to_number не должен превращать пустую строку в 0 или принимать только
  числовой префикс строки вроде "100 неизвестно".
  Перечисленные текстовые и числовые преобразования неприменимы к files.
  Подготовка файлов задаётся типизированной conversion.kind = "files"
  в маппинге площадки; формат этих правил описан в parsing_rule.txt.

depends_on:
  Массив id полей, которые должны быть успешно обработаны раньше.
  Например, модель зависит от марки, цена — от валюты.
  Порядок массива options сам по себе не заменяет явные зависимости.
  Несуществующие ссылки и циклы зависимостей — ошибки спецификации.
  Если зависимость отсутствует или не обработана, поле остаётся ожидающим.

when:
  Условие применимости поля. Отсутствие when означает, что поле применимо.
  Неприменимое поле не заполняется и не считается пропущенным обязательным.

overwrite:
  if_empty — заполнять только пустое поле; режим по умолчанию.
  always   — разрешить замену существующего значения.
  never    — не записывать значение; разрешены чтение и проверка.
  Если текущее значение уже совпадает с требуемым, повторная запись не нужна.
  Для files if_empty сохраняет уже прикреплённую коллекцию; always допускает
  явно предусмотренную замену с проверкой состава. Автоматическое добавление
  к неизвестной коллекции или удаление файлов не подразумевается.
  Продолжение собственной частичной загрузки — восстановление задания,
  а не новая перезапись: оно требует подтверждённых идентификаторов вложений.

file_role:
  Только для files: семантическое назначение коллекции, например product_image,
  product_video или product_document. Роль помогает сопоставлять поля площадок.
  Фото товара и документ о собственности нельзя объединять по одному факту
  наличия input[type=file]. Новая роль должна быть определена в описании поля.

file_policy:
  Только для files. Общие правила обращения с коллекцией:
    keep_original: true        — исходные файлы неизменны;
    ordering: "preserve_source" — сохранять порядок выбранных вложений;
    primary: "explicit"        — главное изображение задаётся явно;
    on_incompatible: "needs_review" — не подменять несовместимые вложения.
  primary используется для коллекций, где имеет смысл главное изображение.
  Параметры сжатия/конвертации под сайт задаются в маппинге, без дублирования
  здесь. Ограничения сайта хранятся в validation его собственного Option.

validation:
  Ограничения значения после преобразования. Подробности — в разделе 6.

Отсутствие значения отличается от 0 и false. Для обязательного текстового
поля пустая после trim строка считается незаполненной. Для обязательного
multi_enum или files пустой массив считается незаполненным.
null обозначает отсутствие, а не команду очистить поле на сайте.

5. УСЛОВИЯ WHEN

Условия используют id полей и их нормализованные значения.
Для enum сравниваются коды choice.fill_rule.value, а не названия вариантов.

Группы условий:
  all — все вложенные условия должны выполниться;
  any — достаточно одного выполненного условия;
  not — отрицание одного вложенного условия.

Операции:
  equals, not_equals — равенство / неравенство;
  in, not_in        — принадлежность / непринадлежность списку;
  exists            — наличие значения;
  gt, gte, lt, lte  — числовые сравнения.

Пример применимости объёма двигателя:

{
  "all": [
    {
      "option_id": "car.fuel",
      "operator": "in",
      "value": ["petrol", "diesel", "hybrid"]
    }
  ]
}

Один узел условия содержит либо all, либо any, либо not, либо листовое
сравнение option_id/operator/value. Смешивать формы в одном узле нельзя.
Для exists свойство value не требуется.
Для in/not_in value — массив скалярных кодов.
Для числовых сравнений требуется число.
Строка "0" не равна числу 0 без явно заданного преобразования.

Если значение ещё неизвестно, сравнение остаётся неопределённым:
not или not_equals не должны превращать неизвестность в разрешение заполнения.
Поле активно только если всё условие определённо истинно.
exists при отсутствии значения возвращает false.
Для files exists возвращает true только для непустой коллекции ссылок.
Это проверка входных данных, а не успешности загрузки. Сравнения строк,
чисел и enum-кодов к коллекции файлов неприменимы. Поле, зависящее от
завершённой загрузки, использует depends_on и ждёт подтверждённого результата.

6. VALIDATION

Для text:
  min_length, max_length — длина текста;
  pattern                — регулярное выражение из доверенной спецификации;
  format                 — например email, uri или phone, если описан валидатор.

Для integer и number:
  min, max               — границы диапазона;
  exclusive_min          — при true значение строго больше min;
  exclusive_max          — при true значение строго меньше max;
  multiple_of            — допустимый шаг, например 0.01.

Для enum и multi_enum:
  allow_custom_value     — можно ли использовать код, которого нет в options;
  min_items, max_items   — число выбранных значений для multi_enum;
  unique_items           — отсутствие повторов для multi_enum.

Для files:
  min_items, max_items   — количество файлов;
  max_file_size_bytes    — максимальный размер одного файла;
  max_total_size_bytes   — суммарный размер;
  mime_types             — допустимые MIME-типы;
  extensions             — допустимые расширения, если подтверждены источником;
  min_width_px, max_width_px, min_height_px, max_height_px — размеры изображения;
  min_duration_seconds, max_duration_seconds — длительность видео;
  min_pages, max_pages   — число страниц документа, если применимо;
  unique_items           — недопустимость повторов по хешу содержимого.

Неизвестное ограничение может быть обозначено null в результате парсинга:
оно требует уточнения и не означает отсутствие лимита. Конкретные размеры,
форматы и обязательность не придумываются. MIME-тип проверяется по содержимому,
а не только по имени/расширению. Общие требования коллекции и требования
выбранной площадки проверяются раздельно. Различающиеся лимиты площадок
не объединяются автоматически в один общий лимит.

Исходные файлы проверяются на доступность, тип и целостность. Затем применяется
явно разрешённая подготовка из маппинга, после чего производные копии проходят
полную validation площадки до передачи загрузчику. Это позволяет, например,
уменьшить исходное изображение до лимита, не объявляя его заранее непригодным.

Для date и datetime:
  min_date, max_date     — включительные границы в формате соответствующего типа.

Неприменимые к типу ограничения, неизвестные свойства и некорректные границы
должны выявляться валидатором спецификации, а не молча игнорироваться.
required: true для boolean означает наличие true или false, а не требование true.

7.1. ПОЛЕ ФОТОГРАФИЙ В ОБЩЕЙ МОДЕЛИ

Следующий Option включается в options той же категории вместе с текстовыми
полями. Его тип files сохраняется и в исходной, и в общей модели:

{
  "id": "product.images",
  "name": "Фотографии товара",
  "description": "Выбранные фотографии товара в заданном порядке",
  "type": "files",
  "fill_rule": {
    "value_from": "attachments.images",
    "file_role": "product_image",
    "overwrite": "if_empty",
    "file_policy": {
      "keep_original": true,
      "ordering": "preserve_source",
      "primary": "explicit",
      "on_incompatible": "needs_review"
    }
  },
  "options": []
}

required и ограничения площадки здесь намеренно не заданы. В реальной
спецификации их указывают по установленным требованиям; наличие фото-поля
не означает обязательность загрузки на каждом сайте.

7.2. ЗНАЧЕНИЕ FILES В ДАННЫХ ОБЪЯВЛЕНИЯ

Пример массива AttachmentReference, на который указывает attachments.images:

[
  {
    "attachment_id": "image-001",
    "source": {"kind": "storage", "ref": "attachments/image-001"},
    "name": "front.jpg",
    "mime_type": "image/jpeg",
    "size_bytes": 245000,
    "position": 0,
    "is_primary": true
  }
]

Значения примера условные. Это данные объявления, а не фрагмент его схемы.
attachment_id стабилен; source указывает на хранилище, а не содержит бинарные
данные. При подготовке добавляются проверенный хеш и технические параметры.
Порядок массива и position должны совпадать; противоречие требует исправления.
is_primary задаёт обложку явно и не может быть true у нескольких элементов.

Для внешнего видео/документа допустим source.kind = "url" с source.ref = URL,
если такой способ поддерживается площадкой. Это остаётся элементом files,
а не общим полем text. По URL нельзя выдумывать размер, MIME-тип или наличие
файла; способ обработки и подтверждения задаёт привязка площадки. Автоматическое
скачивание и преобразование URL в локальный файл не подразумевается.

Файлы хранятся отдельно физически, но их поля входят в ту же Category/Option.
Ни бинарное содержимое, ни временные upload-токены не записываются в схемы.

8. ПРИВЯЗКА К СТРАНИЦЕ — ОТДЕЛЬНЫЙ СЛОЙ

В первоначальном предложении target, action, events, wait_for, timeout_ms
и verify находились в fill_rule. После уточнения универсальности они относятся
к отдельной привязке площадки и НЕ включаются в универсальный Option.fill_rule.
Семантические transform, validation, when и depends_on остаются в Option.

Предлагаемая привязка ссылается на category_id и option_id:

{
  "platform": "example_marketplace",
  "category_id": "cars",
  "option_id": "car.price",
  "target": {
    "selectors": ["input[name='price']", "input#price"]
  },
  "action": "set_value",
  "events": ["input", "change", "blur"],
  "wait_for": ["visible", "enabled"],
  "timeout_ms": 5000,
  "verify": {"kind": "value_equals", "normalize": "number"}
}

Это иллюстрация, а не подтверждённые селекторы конкретной площадки.
Один Option может иметь разные привязки: select на одном сайте, radio или
нестандартный список на другом. Коды площадки сопоставляются с универсальными
кодами отдельно. Например, универсальный "used" может соответствовать "0".

Предлагаемые действия привязки:
  set_value     — записать значение в input или textarea;
  select_option — выбрать вариант нативного select;
  set_checked   — установить нужное состояние checkbox/radio без слепого переключения;
  choose        — выбрать соответствующий вариант;
  click         — нажать явно описанный элемент;
  autocomplete  — ввести текст, дождаться подсказок, выбрать точное совпадение;
  upload_files  — передать файлы в поле загрузки;
  sequence      — выполнить последовательность описанных шагов.

target.selectors — селекторы в порядке приоритета. Если текущий селектор
нашёл несколько подходящих элементов, это ambiguous, а не повод выбирать
первый элемент. Следующий селектор используется, если совпадений нет.

wait_for — готовность элемента; timeout_ms — предельное время ожидания.
verify — проверка принятия результата: value_equals, selected_text_equals,
checked_equals, files_accepted либо другая заранее реализованная проверка.
Успешный вызов click или события input сам по себе не означает принятие данных.

Зависимые элементы ищутся заново после изменения родительского поля:
сайт может заменить HTML, подгрузить варианты или изменить доступность.
Заполнение формы и финальная отправка объявления — разные операции.
Само наличие Category/Option не является командой публикации.

Для files используется action = "upload_files", либо явно описанный ввод
ссылки из AttachmentReference, если сайт работает с URL. В обоих случаях
verify.kind = "files_accepted" проверяет принятие площадкой, состав коллекции,
окончание обработки и отсутствие ошибок. Локальный preview не подтверждает
успешную загрузку. Привязка ссылается на обычный option_id типа files.

9. ПОРЯДОК ПАРСИНГА И ЗАПОЛНЕНИЯ

При парсинге:
  1) Определить категорию и подкатегории, присвоить стабильные id.
  2) Собрать поля, включая загрузку фото/видео/документов, подписи, варианты и коды.
  3) Определить типы, обязательность, зависимости и ограничения по источнику.
  4) Сохранить универсальное дерево Category[].
  5) Отдельно сохранить привязки элементов и кодов конкретной площадки.
  6) Проверить структуру, уникальность id, ссылки и отсутствие циклов.

Файловые поля участвуют в том же сопоставлении между площадками и имеют
записи в том же mapping_%category%_%platform%.json. Отдельный каталог
media-манифестов для них не создаётся.

Неизвестные ограничения, закрытые ветви динамического списка и непроверенные
варианты не нужно выдумывать. Их неполноту следует фиксировать в отдельном
отчёте парсинга. Наблюдение одной страницы не гарантирует покрытие всей категории.

При заполнении:
  1) Выбрать Category по id и передать данные конкретного объявления.
  2) Получить значения через value_from или явно заданный value/default_value.
  3) Выполнить transform, вычислить when и проверить validation.
  4) Построить порядок выполнения по depends_on.
  5) Найти привязки для выбранной площадки и текущей формы.
  6) Дождаться готовности, учесть overwrite и выполнить действие.
  7) Проверить результат через verify; только затем разблокировать зависимые поля.
  8) После изменения формы обновить наблюдение и обработать появившиеся поля.

Для files в шагах 3–7 вызывается файловый обработчик общего исполнителя:
подготовка производных копий, проверка, передача и подтверждение загрузки.
Текстовые обработчики и преобразование коллекции в строку не применяются.
depends_on может связывать файловое поле с обычным и наоборот.

Предлагаемые состояния результата:
  filled         — значение записано и подтверждено;
  unchanged      — требуемое значение уже было установлено;
  not_applicable — условие when ложно;
  waiting        — зависимость, значение или элемент ещё не готовы;
  preserved      — существующее значение сохранено по политике overwrite;
  ambiguous      — неоднозначный элемент либо вариант;
  invalid        — данные или спецификация не прошли проверку;
  unsupported    — отсутствует привязка или обработчик;
  failed         — действие не завершилось подтверждённым результатом.

У files дополнительно отслеживается состояние каждого вложения: pending,
prepared, uploading, processing, accepted, rejected, needs_review, unsupported,
failed или unknown. Общее filled допустимо только после подтверждения всей
назначенной коллекции и её требований. Частичный успех не считается полным;
зависимые поля не разблокируются при неизвестном исходе загрузки.

10. ГРАНИЦЫ ЭТОГО ДОКУМЕНТА

Документ фиксирует формат и предлагаемые правила для дальнейшей разработки.
Наличие спецификации не означает, что универсальный парсер, валидатор,
исполнитель всех действий или миграция существующего каталога уже реализованы.
При развитии формата нужно версионировать спецификацию и привязки, сохраняя
корневой контракт Category[]. Метаданные версии можно хранить отдельным файлом.
