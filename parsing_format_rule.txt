ФОРМАТ РЕЗУЛЬТАТОВ ПАРСИНГА
Документ: parsing_format_rule.txt
Версия: 2.2 | Редакция инструкции: 2026-11-12

Здесь определена структура данных; порядок работы — в parsing_rule.txt.
parsing_input.txt заполняет и изменяет только человек, выдающий задание.
Для ИИ это вход только для чтения. Спецификация не означает, что исполнитель
всех описанных действий уже реализован в расширении.

Два отдельных задания: A создаёт исходные Category[] и binding площадки;
B сравнивает готовые Category[] и создаёт common/mapping без изменения входов.
В B сопоставляются name полей и name дочерних choice внутри enum/multi_enum;
Для плоских списков mapping связывает общий текст с исходным choice.value;
для деревьев childOptions — ID узлов на каждом уровне, см. раздел 2.1.
Появление новых схем само по себе не запускает B. Границы этапов — в parsing_rule.txt.

1. CATEGORY И OPTION

Корень файла категории — Category[]. Обязательные свойства:

interface Category {
  id: string;
  name: string;
  description: string;
  categories: Category[];
  options: Option[];
}

interface Option {
  id: string;
  name: string;
  description: string;
  type: OptionType;
  options: Option[];
}

id стабилен; name/description предназначены человеку. Массивы всегда присутствуют.
Category.id уникален в каталоге, Option.id — в дереве одной категории.
Подкатегории находятся в categories; поля — в options. Автоматического
наследования полей нет. В новых схемах 2.2 fill_rule не создаётся. Для чтения схем аренды 1.2 см. раздел 7.

Допустимые дополнительные свойства Option — факты о поле, а не команды браузера:
  value            — обязательно для исходного choice: код площадки; null, если неизвестен;
  required         — true/false; null при неизвестной обязательности;
  validation       — ограничения из раздела 3;
  when             — условие применимости из раздела 3;
  file_role        — для files: product_image/product_video/product_document
                     либо иная явно описанная роль;
  options_complete — обязательно для enum/multi_enum: подтверждена ли полнота списка.
  childOptions     — дочерние choice дерева, не поля и не категории (раздел 2.1);
  level            — у choice дерева: id объявленного enum-поля своего уровня;
  parent_option_id — у зависимого enum-поля дерева: id поля предыдущего уровня.
У choice дерева options_complete описывает полноту непосредственных childOptions.

Исходные типы: group, text, integer, number, boolean, date, datetime,
enum, multi_enum, choice, files. group.options содержит поля/группы.
text включает телефоны, VIN и артикулы: ведущие нули не теряются.
date — YYYY-MM-DD, datetime — ISO 8601 с часовым поясом.
files — коллекция ссылок на фотографии, видео или документы.
У конечных полей, кроме перечислений, options = []; у choice — также [].
Общий файл сохраняет group/files, остальные конечные поля имеют тип text,
кроме полей дерева childOptions: они сохраняют enum и choice (раздел 2.1).
Значения конкретного объявления и способы установки полей в схему не записываются.

2. ENUM И ВАРИАНТЫ ВЫПАДАЮЩЕГО СПИСКА

Option типа enum ОБЯЗАТЕЛЬНО содержит options: Option[] со всеми наблюдаемыми
вариантами выпадающего списка. Для multi_enum действует то же правило.
Каждый вариант — отдельный Option типа choice: id, name, description, type,
value и options: []. name — видимая подпись, value — нативный код, не порядковый
номер и не придуманный перевод. Тип кода сохраняется: строка "01" не равна числу 1.
Служебный placeholder вроде «Выберите» не считается значением, если он недоступен
для выбора. Disabled/недоступные в текущей ветви варианты отмечаются в отчёте.

Если подпись видна, но код неизвестен, сохранить choice с value: null;
не прятать известные варианты только в description и не оставлять options пустым.
options_complete: true допустимо лишь после проверки всего доступного списка
для указанного состояния, включая пагинацию. При неполноте — false и отчёт
о границе покрытия. [] допустим только если варианты вообще не удалось наблюдать.
Полнота списка и известность кодов — разные факты: неизвестные коды не выдумываются.

childOptions использовать для цепочек, явно выбранных в задании, по разделу 2.1.
Наличие зависимости само по себе не требует создавать дерево. Для остальных
зависимых списков сохранять плоский массив options и связь через when варианта;
наблюдаемые варианты разных ветвей не выдавать за безусловно доступные.
Динамические подсказки не выдавать за полный справочник. Непроверенные варианты
не заполняются автоматически. При неизвестном коде выбор по подписи допустим
только через подтверждённый однозначный binding с match: "text".

2.1. ДЕРЕВЬЯ CHILDOPTIONS И ПРЯМОЙ МАППИНГ УЗЛОВ

Нормативное продолжение контракта: docs/parsing/child-options-contract.txt.
Примеры полного синтаксиса: docs/parsing/examples/child-options/.
Эти правила общие для категорий, а не специальная схема конкретного товара.

options содержит варианты поля текущего уровня; childOptions внутри choice —
варианты следующего уровня. У каждого узла обычный стабильный id, name,
description, type: choice, options: [], level и childOptions. Нового вида ID
не вводится. У исходного узла value — нативный код; у общего узла выбор задаётся
его id, value не нужен. Корневое и зависимые enum-поля объявляются отдельно;
level ссылается на поле, parent_option_id связывает уровни. Каждый choice хранится
в дереве ровно один раз. Подробные правила пустых options и полноты — в продолжении.

Узел имеет одного родителя; индекс родителей строится по вложенности. Разрешён
выбор промежуточного узла: храним его id как значение корневого поля карточки,
восстанавливаем только предков. Пустые childOptions с options_complete: false
означают неизвестную ветвь, а не отсутствие дочерних вариантов. Годы и даты не
добавляют уровней и не используются для фильтрации/сопоставления узлов этого
дерева; варианты собираются вместе. Наблюдаемые дополнительные ограничения
площадки сохраняются отдельно в when и отчёте, не игнорируются при заполнении.

На B сравнивать имена и смысл узлов в контексте уже сопоставленных родителей.
Сохранять прямые связи ID на каждом уровне, включая промежуточные. Не использовать
finalId, поиск обходного пути по конечному узлу, неявный fallback или первый вариант.
Одинаковое имя само по себе не доказывает соответствие. Неоднозначность — needs_review.

Версия 2.2 — исследовательский контракт. Текущие SchemaCompatibility и исполнитель
поддерживают прежние версии, не childOptions/node_lookup. До отдельной реализации
нельзя активировать новый формат в data/rental/manifest.json, выдавать старый
валидатор за проверку 2.2 или автоматически мигрировать недвижимость.

3. WHEN, VALIDATION И FILES

when: {"all": [условия]} | {"any": [условия]} | {"not": условие}
либо {"option_id": "id", "operator": "операция", "value": значение}.
Операции: equals, not_equals, in, not_in, exists, gt, gte, lt, lte.
Для in/not_in value — массив, для exists не нужно; ссылки — на поля этой категории.
Сравниваются коды/типизированные значения; неизвестность не превращается в истину
через отрицание. Для files exists проверяет непустую коллекцию, не факт загрузки.
При переносе условия в common нужно сопоставить id и универсальные значения.

validation:
  text: min_length, max_length, pattern, format (email/uri/phone);
  числа: min, max, exclusive_min, exclusive_max, multiple_of;
  enum: allow_custom_value;
  multi_enum: allow_custom_value, min_items, max_items, unique_items;
  date/time: min_date, max_date;
  files: min_items, max_items, mime_types, extensions, max_file_size_bytes,
         max_total_size_bytes, min_width_px, max_width_px, min_height_px,
         max_height_px, min_duration_seconds, max_duration_seconds,
         min_pages, max_pages, unique_items.

Указывать только применимые подтверждённые требования; null — неизвестность,
а не отсутствие лимита. 0 и false — значения, не отсутствие. required: true
не допускает пустую строку/коллекцию, но допускает boolean false.
Лимиты и обязательность площадки не становятся автоматически общими.

Files участвует в тех же категориях и маппингах. Значение — массив ссылок
на исходные вложения, не строка и не дочерние Option. Роль различает фото товара
и сканы документов. Подготовка файлов относится к mapping, загрузка — к binding.
Оригиналы, порядок и явно выбранная обложка сохраняются; молчаливое обрезание,
отбрасывание части коллекции и бинарные данные в спецификации не допускаются.

4. MAPPING — ПРЕОБРАЗОВАНИЕ ДАННЫХ

Файл mapping_%category%_%platform%.json:
  {category_id, platform, fields: [{common_option_id, platform_option_id, conversion}]}.
Для нескольких входов вместо common_option_id — common_option_ids: [id, ...]
с явным назначением входов. Ссылки разрешаются в common и исходной схеме площадки.
Для дерева дополнительно nodes: [{common_option_id, platform_option_id}]. Здесь
ID ссылаются на choice, а fields — на поля уровней. nodes содержит только прямые
подтверждённые связи; source value извлекается из целевого choice. Оба конца и все
предки проверяются по контракту childOptions. Без дерева nodes можно опустить.

Создаётся только на этапе B по отдельному заданию. Для плоских enum значения from —
канонический текст по результату сравнения choice.name, to — исходный choice.value.
Переименование подписи не меняет нативный код. Несопоставленные значения остаются
кандидатами/needs_review; исходные options и binding на этапе B не переписываются.

conversion.kind:
  identity — перенос без преобразования;
  lookup   — values: [{from, to}, ...], on_unmapped: "needs_review";
  node_lookup — только поля дерева: прямые связи из nodes, on_unmapped: "needs_review";
  files    — preparation: {operations: [...]}, on_incompatible: "needs_review".
node_lookup описывает требуемое преобразование 2.2, не существующий runtime-handler.
Для enum результат lookup соответствует choice.value. Неизвестный код нельзя
подменять null как готовым результатом; сопоставление остаётся кандидатом.

Операции файлов задаются явно: resize_image (размеры, keep_aspect_ratio),
compress_image (пределы качества), convert_image (mime_type), normalize_orientation.
Пустой operations разрешает только перенос уже совместимых файлов без изменения.
Для преобразований чисел/дат/единиц/списков задавать точные форматы и параметры;
если обработчик не определён заданием, описать кандидат в отчёте, не изобретать
исполняемый код. Маппинг не считается обратимым автоматически.

5. BINDING — ПРАВИЛА ЗАПОЛНЕНИЯ СТРАНИЦЫ РАСШИРЕНИЕМ

Файл binding_%category%_%platform%.json (binding в единственном числе):
  {category_id, platform, fields: [Binding, ...]}.
Он создаётся при каждом парсинге площадки, в том числе до появления common.

Для каждого конечного поля исходной схемы, включая files, создаётся одна запись:
  option_id  — id поля площадки, не common и не дочернего choice;
  status     — ready / needs_review / unsupported;
  reason     — обязательно для неготовой записи; что не проверено или не поддерживается.
Для group и choice отдельная запись не требуется. Условные варианты исполнения
одного поля описываются через steps/условия, а не неоднозначные дубли option_id.
Для дерева запись нужна для каждого объявленного enum-поля уровня, включая поля
с options: [], чьи варианты находятся в childOptions. В binding не дублируй дерево.

У ready обязательны target, action, verify; по необходимости добавляются:
  target: {selectors: [CSS, ...]} — приоритетные наблюдаемые селекторы;
  action: set_value / select_option / set_checked / choose / click /
          autocomplete / upload_files / sequence;
  match: "value" / "text" — способ точного сопоставления enum;
  events: ["input", "change", "blur"];
  depends_on: [option_id, ...] — порядок после успешного заполнения родителей;
  overwrite: "if_empty" (по умолчанию) / "always" / "never";
  wait_for: ["visible", "enabled"], timeout_ms;
  verify: {kind: value_equals / selected_text_equals / selected_text_set_equals /
                 checked_equals / files_accepted}.

Если элемент действия и элемент чтения результата различаются, verify может
содержать target: {selectors: [CSS, ...]}. Без verify.target читается target
самого binding. Для selected_text_equals target проверки должен находить только
выбранный вариант/значение, а не всю группу с текстами всех вариантов. Для
checked_equals на input читается свойство checked, а не строка aria-checked.
Невидимый нативный checkbox допустим как target set_checked, если его видимый
контрол действительно доступен в этой ветви: wait_for не включает visible для
самого hidden input. Установка идемпотентна, результат проверяется после обновления
формы. Эти уточнения относятся к исследовательскому контракту, не добавляют
поддержку 2.2 в существующий runtime.

Для multi_enum с popup и подтверждением допустим проверенный choose:
  selection_mode: "replace_set";
  suggestions: {selector: CSS элементов вариантов, match: "exact_text",
                checkbox_selector: CSS нативного checkbox внутри варианта};
  commit: {target: {selectors: [CSS кнопки применения]}};
  verify: {kind: "selected_text_set_equals", target: {selectors: [CSS popup]},
           items_selector: CSS выбранных вариантов внутри popup, reopen: true}.
Вход — полный массив кодов choice.value; подписи берутся из схемы. До изменения
проверить наличие ровно одного варианта для каждого входного значения. Снять
лишние отметки, поставить недостающие; пустой массив означает очистить всё.
После commit дождаться закрытия popup, открыть его заново и сравнить ПОЛНОЕ
множество выбранных подписей, без зависимости от порядка. Нулевое число элементов
items_selector допустимо только для ожидаемого пустого множества; сам popup должен
существовать. После проверки закрыть popup тем же commit. Несовпадение или timeout
не считается успехом. items_selector, в отличие от target, обозначает коллекцию.
overwrite по-прежнему применяется до выполнения действия; replace_set не даёт
права заменять пользовательские данные при overwrite=if_empty/never.

Для files_accepted допускается конкретный проверенный рецепт серверных фото:
  target — уникальный контейнер коллекции;
  items_selector — карточки файлов внутри контейнера;
  image_selector — ровно одно изображение внутри каждой карточки;
  accepted_src_prefix — наблюдённый HTTPS-префикс серверного ресурса;
  require_loaded: true — img.complete и naturalWidth > 0;
  counter_target — уникальный счётчик принятых файлов, если он есть.
Для наблюдённого CSS-превью допускается image_source: "background_image"
(по умолчанию — "img"). image_selector тогда находит ровно один элемент
с computed background-image внутри каждой ПРИНЯТОЙ карточки. Разрешён один
url("...") / url('...'); none, градиенты и несколько фоновых слоёв не считаются
принятым изображением. Проверить HTTPS origin/path accepted_src_prefix,
исключить blob/data URL. require_loaded означает загрузить именно этот URL
через Image и дождаться complete && naturalWidth > 0 && naturalHeight > 0;
обработать onerror/timeout, не считать наличие CSS успешной загрузкой.
items_selector должен исключать шаблонные карточки и индикаторы ожидания.
Если счётчик показывает остаток, допустим counter: {mode: "remaining",
capacity: N, pattern: REGEXP, empty_pattern: REGEXP}. Первая группа pattern —
целый остаток, равный N минус ожидаемое число принятых файлов. empty_pattern
допустим только при ожидаемом нуле и отсутствии принятых карточек. Регулярные
выражения применяются без учёта регистра к тексту с нормализованными пробелами.
Неизвестный текст счётчика — ошибка проверки, а не повод её пропустить.
Ожидаемая коллекция при разрешённом добавлении включает уже принятые файлы;
повторная попытка не даёт права дублировать их или обходить overwrite.
Эти свойства расширяют исследовательский контракт 2.2, не включают их
исполнение в существующем расширении автоматически.
Число карточек и счётчик должны соответствовать ожидаемой коллекции; blob/data URL,
ошибка загрузки, локальный preview и один change недостаточны. Локатор input
необходимо заново разрешать после загрузки: площадка может заменить его. Нельзя
исполнять неподдерживаемые свойства этого исследовательского рецепта как обычный
choose/upload_files: runtime обязан явно поддержать их или остановиться.
Для set_checked с отдельным verify.target исходное и итоговое checked читается
с него, действие выполняется по target только при несовпадении. Дождаться обновления
формы и устойчивого результата; один немедленный readback недостаточен.

Расширение получает подготовленные значения по точному ключу option_id:
результат mapping или отдельный ввод уникального поля. option_id с точкой —
один ключ, не путь к объекту. Binding не хранит личные данные, value_from,
default_value и бизнес-преобразования: подготовка значения относится к mapping.
Применимость/ограничения читаются из Option.when/validation, без дублирования.
Для неготовой записи исполняемые свойства можно опустить; она не выполняется.

Нативный select: target на select, action = select_option, match = value;
варианты и их коды берутся из Option.options, а не дублируются в binding.
Для дерева варианты соответствующего level берутся из активной ветви childOptions.
Нестандартный список: target на открывающий элемент, action = choose или
autocomplete; suggestions: {selector: CSS, match: "exact_text"} описывает
область вариантов. Выбирается точное уникальное совпадение с choice.name.
Для радио/чипов допустим choices: [{choice_id, target, action, verify}],
ссылки ведут на дочерние choice; action = set_checked/click, не слепое переключение.
Если этого недостаточно, описать непроверенный сценарий в reason, не объявлять ready.

Для проверенного смешанного контрола (кнопки + native select одного поля)
допустим choose с suggestions.selector, объединяющим кнопки и option,
match: "exact_text" и suggestions.option_action: "select_option".
Для скалярного integer подпись ищется по десятичной строке входного значения,
без enum/options в схеме. Для enum по-прежнему используется choice.name.
В общей коллекции должен быть ровно один точный кандидат. Ноль/несколько —
ошибка без изменения формы; нельзя брать ближайшее значение или первый вариант.
Для option заново найти владеющий select, проверить disabled у него и option,
установить нативное значение option и отправить events (input/change).
Не нажимать option как обычную кнопку и не требовать видимости закрытого option;
сам select/его видимый контрол должен быть доступен. Для кнопки выполняется click.
Итоговый selected_text_equals читает только один активный контрол: например,
активную кнопку либо option:checked внутри активного контейнера select.
Скрытый/устаревший select не является источником результата при активной кнопке.
Привязка не содержит диапазонов дат или списков вариантов, вычисляемых по часам
исполнителя; доступность берётся из текущего DOM. Правило требует явной поддержки
runtime, как и остальные расширения исследовательского контракта.

sequence содержит steps: [{target, action, ...}], каждый шаг — подтверждённое
действие. У шага допускается when по правилам раздела 3. Итоговое verify поля
обязательно; произвольные скрипты и финальная публикация в steps не допускаются.

Селекторы перебираются по порядку: нет совпадений — следующий; несколько —
неоднозначность, не первый элемент. Зависимости без циклов и отсутствующих id.
После выбора родителя элементы ищутся заново. Files использует upload_files
или ввод поддерживаемой ссылки; verify = files_accepted требует подтверждения
площадкой, а не одного change/preview. Нельзя утверждать поддержку расширением
непроверенного обработчика только по наличию корректного JSON.

7. КАК ЧИТАТЬ СОХРАНЁННЫЙ КОМПЛЕКТ АРЕНДЫ

Ниже описана раскладка для сверки, а не новая версия JSON. C = apartments_long_term_rent; P = kufar, realt, onliner или domovita. Пути заданы от корня репозитория.

data/parsing/C/C_P.json, bindings_C_P.json и report_C_P.txt (три файла в одном каталоге) — первоначальное наблюдение. В схемах 1.2 свойства поля лежат в fill_rule, в том числе код в choice.fill_rule.value. Исторические bindings_C_P.json имеют корень-массив, местами пустой. Отсутствие записи означает отсутствие доказанной привязки в этом снимке.
data/rental/C/P/C_P.json — уточнённая схема площадки. Рядом лежит исторический bindings_C_P.json. При сравнении файлов одинакового имени сохраняй их разные пути.
data/rental/C/integration/C_common.json — Category[] рабочего общего справочника. Здесь 10 групп и 114 конечных полей. Среди листьев 53 text, 26 boolean, 17 enum, 6 multi_enum, 5 integer, 1 number, 2 date и 4 files. Рабочий файл расширен относительно исследовательского common. Правило text/files в разделе 1 относится к плоским полям вновь создаваемого общего результата этапа B; для childOptions действует исключение enum/choice. Существующий типизированный файл нельзя переписать по этому правилу.
data/rental/C/integration/mapping_C_P.json — зафиксированные исследовательские связи. Корень {category_id, platform, fields}; fields содержит направления от common к ID площадки. Количество записей не равно количеству подготовленных или успешно заполненных контролов.
data/rental/C/manifest.json — ссылки common, card, platforms[P].schema, plan, browser. У аренды format_version = 1, source_schema_version = "1.2". При активации схемы 2.1 нужна также ссылка binding. В data/rental/categories.json ключ категории выбирает reference, analysis и разрешение publication.
data/rental/C/runtime/card.json — версия 2 модели карточки, группы, canonicalValues, подписи и адресные зависимости. runtime/preparation_P.json — исполняемый план версии "1.0": fields с преобразованиями, constants для выбранной ветви, отдельные правила и проверки площадки. runtime/browser_P.json — наблюдаемые элементы и шаги формы для расширения. Сервер сверяет schema_hash и common_hash плана с SHA-256 компактной сериализации JSON Jackson. Для отчёта исследования SHA-256 считай по байтам файла и указывай метод. Версию исходной схемы, плана и модели карточки записывай отдельно.

Контрольный срез на ревизии 66a80f5. Числа ниже пересчитывают при изменении данных.
Площадка | листья первоначальной схемы | листья рабочей схемы | записи integration mapping.fields | записи runtime preparation.fields
Kufar    | 25 | 53 | 15 | 37
Realt    | 52 | 59 | 15 | 51
Onliner  | 16 | 20 |  8 | 18
Domovita | 27 | 34 |  7 | 27
Лист — поле произвольной глубины, кроме group и choice. Массивы constants, адресные правила и browser.controls в число записей fields не входят.

Примеры, воспроизводимые по этим JSON:
• Комнаты. В C_common.json поле rental.room_configuration хранит строку. При вводе "2" цепочка common → integration mapping → choice.fill_rule.value даёт kufar.rooms = "2", realt.rooms = 2, onliner.room_count = "2_rooms", domovita.rooms = 2. Для исходного наблюдения 2.1/2.2 читается choice.value. "studio", "5" и "5+" проверяй отдельно.
• Валюта. В исследовательском mapping Kufar для rental.currency есть USD и EUR. В рабочей схеме kufar.currency у варианта «р.» код "BYR", а рабочий план содержит {"from":"BYN","to":"BYR"}. На Realt значение BYN даёт строку "933", на Onliner и Domovita — "BYN". Все четыре результата относятся к одной валюте; сумма остаётся в исходной валюте.
• Цена. В runtime/preparation_onliner.json вход rental.monthly_price связан с onliner.price_amount через {"kind":"decimal","target":"number","requires":["onliner.price_currency"],"currency_field":"onliner.price_currency","integer_currencies":["USD"]}. Исследовательский identity для такого преобразования неверен.
• Файлы. media.images связано с kufar.photos, realt.photos, onliner.images и domovita.images через files. Подготовка с operations: [] сохраняет оригиналы. Этот mapping не содержит селектора загрузчика и не подтверждает приём фото площадкой.
• Постоянное значение. В плане Onliner constants содержит {"onliner.rent_type":"flat"} для квартиры целиком. Наличие нативной альтернативы room в схеме не расширяет границы категории.

Здесь представлены реальные примеры обработчиков исполняемого плана: identity, lookup, files, decimal, multi_lookup, list_lookup, phone и plain_text_html. Перед использованием смотри параметры конкретной записи, версию плана и ограничения цели. Исследовательский mapping 2.2 ограничен своим контрактом. node_lookup из 2.2 ещё не входит в этот список исполняемых обработчиков. Если результат требует отдельного обработчика, укажи вход, ожидаемый типизированный выход, условия и пробел в отчёте.
